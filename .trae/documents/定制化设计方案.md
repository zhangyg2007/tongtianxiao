## 0. 核心结论

### 0.1 一句话

**把 RAGFlow 作为"证据层"独立部署，把 bettafish 保留为"分析与写作层"，两者通过 HTTP 检索接口连接；结构化事实（工商/股权/事件/预警）落在 PostgreSQL，不塞进向量库。**

### 0.2 选型结论

| 决策项 | 结论 | 关键理由 |
|---|---|---|
| 知识库 | **RAGFlow 主用**，MaxKB 不用（除非要买企业版做对话前端） | RAGFlow 是 Apache-2.0，可商用可闭源集成；MaxKB 是 GPLv3，且**社区版没有平台级 API**，无法作为"检索微服务"被调用 |
| 检索接口 | RAGFlow REST `/api/v1/retrieval` | 直接返回 `content` / `similarity` / `document_id` / `document_name`，足够拼证据链 |
| 结构化库 | PostgreSQL（复用现有实例，新建 `kb` schema） | bettafish 已强依赖 PG；避免再引一套 MySQL |
| 向量库 | 由 RAGFlow 自带的 Elasticsearch/Infinity 承担 | 不在 PG 里重复存一份 chunk 向量 |
| 图查询 | **先用 PG 递归 CTE + 闭包表**，不急着上 Neo4j | 股权穿透是固定深度、固定边类型的查询，PG 够用；Neo4j 只在 P3 有明确需求时再评估 |
| bettafish 改造 | **只增加一个检索工具，不改引擎主循环** | `InsightEngine/agent.py:190` 的 `execute_search_tool` 是现成的分发器 |
| 新增第 4 个引擎？ | **不新增** | 报告门禁硬依赖"恰好三份新 `.md`"（`ReportEngine/agent.py:1602-1661`），加第四个源会让门禁复杂度翻倍 |
| 事件时间线 / 声量曲线 / 情感拐点 | **放独立服务，不放 bettafish** | bettafish 的 LLM 循环是"写作"不是"时序计算"；且其执行绑定浏览器会话 |

### 0.3 最大风险（按严重程度）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| 1 | **数据可得性风险 > 技术风险** | 最难的不是 RAG，是拿到合法、稳定、可更新的工商/招投标/裁判文书数据。见 §4 | 能买就买（天眼查/巨潮/剑鱼），爬虫只做补充 |
| 2 | **实体对齐准确率** | 同名不同主体、简称/曾用名混用会导致"把 A 公司的处罚挂到 B 公司头上"，这是背调类产品的致命错误 | 统一社会信用代码为唯一主键 + 人工复核队列 + 置信度分级，见 §5 |
| 3 | **LLM 幻觉污染事实** | 报告里一句编造的"被罚 200 万"会毁掉整个产品可信度 | 所有事实句强制携带 `evidence_id`，无证据即拦截，见 §8.1.4 |
| 4 | **GPL 传染（若选 MaxKB）** | 若未来要"交付镜像给客户私有化部署"，GPLv3 会要求开源全部对应源码 | 选 RAGFlow 即规避 |
| 5 | RAGFlow 1.0 是两天前的新版本 | v1.0.0 于 2026-11-06 发布，含破坏性变更（`chunk_method` → `parse_type`） | 锁定 tag，等 1.0.x 补丁；不要跟 main |

### 0.4 证据等级约定

- **✅ 已核实**：本次实际访问了官方文档 / GitHub 原文 / 仓库代码，附 URL 或文件行号
- **⚠️ 待验证**：官方未明确说明、需实测或需向厂商确认
- **📐 估算**：基于代码结构与经验推算，无实测数据

## 1. 系统定位与总体架构

### 1.1 业务目标

把 bettafish 从"输入主题 → 出一份舆情报告"的**单点工具**，升级为：

> **输入一个公司名或一个事件 → 自动汇聚工商、司法、财务、招投标、舆情五类证据 → 输出可溯源的结构化背调 / 事件脉络 / 风险预警 / 处置建议**

### 1.2 分层架构

```text
┌─────────────────────────────────────────────────────────────────────┐
│  应用层（新增）：背调报告 / 事件追踪 / 预警看板 / 预案库              │
│  Flask 主应用（复用 bettafish app.py，新增若干 Blueprint）            │
└───────────────┬──────────────────────────────┬──────────────────────┘
                │                              │
┌───────────────▼──────────────┐  ┌────────────▼──────────────────────┐
│ 分析层（复用 bettafish）      │  │ 事实层（新增）                     │
│ QueryEngine  全网调研         │  │ events / alerts / scores          │
│ MediaEngine  多模态           │  │ 独立 Python 批处理服务             │
│ InsightEngine 本地库深挖 ─────┼─▶│ 声量曲线 · 情感拐点 · 事件聚类     │
│ ReportEngine IR → HTML/PDF    │  │ ReportEngine IR → HTML/PDF         │
└───────────────┬──────────────┘  └────────────┬──────────────────────┘
                │                              │
        ┌───────▼──────────────────────────────▼───────┐
        │ 证据层                                          │
        │ RAGFlow（文档原文 + 向量 + 混合检索）           │
        │ PostgreSQL `kb` schema（公司/人物/事件/证据）   │
        └───────────────────────┬───────────────────────┘
                                │
        ┌───────────────────────▼───────────────────────┐
        │ 采集层：AkShare/Tushare · 天眼查 · 巨潮 · OSINT │
        └───────────────────────────────────────────────┘
```

### 1.3 与 bettafish 的关系

| 模块 | 处置 | 说明 |
|---|---|---|
| `app.py` Flask 主应用 | **复用**，新增 Blueprint | 已有 Blueprint 注册范式（`app.py:78-83`） |
| QueryEngine | **保留**，可选注入知识库工具 | 全网 OSINT 采集能力强，是"公开信息情报"的主力 |
| MediaEngine | **保留不动** | 与背调场景弱相关，但报告门禁需要它 |
| InsightEngine | **重点改造**（新增 1 个工具） | 从"本地舆情库"扩展为"本地舆情库 + 行业知识库" |
| ReportEngine | **复用渲染层**，新增报告模板 | IR 抽象是全项目最干净的一层，加输出格式成本低 |
| ForumEngine | 保留 | 报告门禁检查 `logs/forum.log` 是否存在 |
| MindSpider | 保留，扩展采集源 | 已有 7 平台 MediaCrawler |

## 2. 合规边界与数据治理（必须前置）

> 这一节不是法务免责声明，而是**产品设计的硬约束**。越界的字段不进表、不进 prompt、不进报告。

### 2.1 数据范围白名单 / 黑名单

**白名单（只用这些）**

| 类别 | 具体来源 | 性质 |
|---|---|---|
| 工商公示 | 国家企业信用信息公示系统、天眼查/企查查 | 依法公示 |
| 上市公司公告 | 巨潮资讯、交易所网站 | 法定披露 |
| 司法公开 | 中国裁判文书网、人民法院公告网、执行信息公开网 | 依法公开 |
| 行政处罚 | 信用中国"双公示"、地方市场监管局 | 依法公示 |
| 招投标 | 中国招标投标公共服务平台、各地公共资源交易中心 | 依法公开 |
| 知识产权 | 国家知识产权局（专利）、中国商标网 | 依法公示 |
| 监管问询 | 交易所问询函、证监会行政处罚决定书 | 依法公开 |
| 公开新闻 | 财经媒体、门户、已授权转载源 | 公开传播 |

**黑名单（一律不采集、不存储、不推断）**

- 身份证号、护照号、社保号
- 手机号、邮箱、通讯地址（自然人）
- 亲属关系、婚姻状况、健康状况
- 行踪轨迹、住宿记录、消费记录
- 金融账户、征信报告
- 未公开的内部文件、泄露数据、付费墙后抓取内容

> 设计后果：**人物实体没有唯一标识**。这不是缺陷，是约束——见 §5.4 的处理方式。

### 2.2 合法性依据与边界

1. **处理的是"已公开"信息**，且处理目的是**企业风险管理**，不是对自然人的画像或营销。
2. **不得绕过技术措施**：不破解验证码、不伪造登录态、不规避频率限制。对明确禁止爬取的站点（robots.txt / 用户协议），走商业采购。
3. **公开 ≠ 可自由转售**：工商、司法、舆情数据的**二次销售**可能触碰平台协议与《反不正当竞争法》。若产品对外售卖，数据源必须换成有商用授权的 API。
4. **不发布、不传播**：预警结果仅在企业内部流转，不对外公开指名道姓地做负面定性。

### 2.3 个人信息最小化（三条硬规则）

1. **只存"公开职务身份"**：高管只存"姓名 + 任职公司 + 职务 + 任期"，来源是工商公示与上市公司公告。
2. **不做人物画像**：不汇总某人的全部关联公司形成"个人档案页"；只在公司维度展示"该公司的高管名单"。
3. **如需去重，用单向哈希**：若上游数据带身份证号，**入库前丢弃**；如确需跨源去重，存 `HMAC-SHA256(id_number, salt)`，不可逆且 salt 独立保管。

> 注：天眼查"人员所有公司"接口（6 元/次）天然返回个人关联企业全景，**这属于人物画像，建议不采购该接口**。

### 2.4 内部权限控制建议

| 措施 | 具体做法 |
|---|---|
| RBAC | 角色：查看者 / 分析员 / 管理员。敏感页（预警详情、原始证据）限分析员以上 |
| 最小授权 | 数据按"项目/客户"分域，跨域默认拒绝 |
| 审计 | 每次查询与导出写 `kb.audit_log`（who / what / when / ip / 结果条数） |
| 导出管控 | 导出文件加水印（账号 + 时间戳）；批量导出需二次确认 |
| 留存期限 | 原始证据文档保留 N 年，到期归档或删除；预警记录保留 ≥ 2 年 |
| 脱敏 | 报告对外版本自动隐藏自然人手机号等（本项目本就不采集） |

## 3. A. 知识库选型：RAGFlow vs MaxKB

### 3.1 对比总表

| 维度 | RAGFlow | MaxKB |
|---|---|---|
| 定位 | 深度文档理解的 **RAG 引擎 / 检索服务** | **对话式知识库问答应用**（1Panel 生态） |
| 开源协议 | **Apache-2.0** ✅ | **GPLv3** ✅ |
| 最新版本 | v1.0.0（2026-11-06）✅ | v2.10.8-lts（2026-10-22）✅ |
| 文档解析 | DeepDoc：OCR + 版面分析 + 表格结构识别 ✅ | 偏向纯文本抽取；**无内置 OCR**，需外接 TextIn 或自建 ✅ |
| 跨页表格 | ⚠️ 官方未明确承诺自动合并 | ⚠️ 未承诺 |
| 检索方式 | 向量 + BM25 全文 + 混合权重 + rerank + GraphRAG ✅ | 向量 / 全文 / 混合（含重排模型）✅ |
| 检索 API | `POST /api/v1/retrieval`，返回 chunk + 3 路分数 + 文档名 ✅ | **社区版无平台 API**；仅 OpenAI 兼容的对话接口 ✅ |
| 建库/上传 API | 有（`/datasets`、`/datasets/{id}/documents`）✅ | 平台 API 属 **X-Pack（专业版）** ✅ |
| 部署依赖 | ES/Infinity + MySQL + MinIO + Redis + NATS（5+ 容器）✅ | maxkb + pgsql + redis（3 容器）✅ |
| 硬件 | 推荐 4C/16G/50G，CPU 即可 ✅ | 4C/8G/100G，CPU 即可 ✅ |
| 二次开发 | 后端 1.0 起为 Go（Python 仅 DeepDoc/RAG），前端 React ✅ | 后端 Python/Django + LangChain，前端 Vue ✅ |
| 商用限制 | 无附加条款；**不授予商标使用权**（Apache §6）✅ | GPLv3：内用无义务；**分发即须开源** ✅ |

### 3.2 协议核查（已核实原文）

**RAGFlow**
- `LICENSE` 为标准 Apache License 2.0 全文，无附加条款，仓库内无 `NOTICE` 文件、`web/` 无独立 LICENSE。
  来源：https://raw.githubusercontent.com/infiniflow/ragflow/main/LICENSE
- 唯一限制是 Apache 2.0 第 6 条（商标）：不得使用 "RAGFlow" 名称与 Logo 做商业背书。
- **结论：可以闭源集成、可以商用、可以私有化交付，只需保留版权声明，不要在宣传物料上用它的品牌。**

**MaxKB**
- `LICENSE` 首行即 "GNU GENERAL PUBLIC LICENSE Version 3"，README 明确 "Licensed under GPLv3"。
  来源：https://raw.githubusercontent.com/1Panel-dev/MaxKB/main/LICENSE
- 社区版免费不限容量；专业版 4.8 万元/套（永久、单实例、含首年维保）；企业版联系销售。
  来源：https://maxkb.cn/price
- **GPLv3 的准确含义**：
  - 企业内部部署、修改自用 → **不构成"分发（convey）"**，无开源义务；
  - 若把**镜像 / 安装包交付给客户私有化部署** → 构成分发，须按 §6 提供**完整对应源码**，且不得加额外限制；
  - 通过网络提供 SaaS，GPLv3 **不同于 AGPL**，不因"网络访问"本身触发开源义务；
  - bettafish 通过 HTTP 独立进程调用，通常属"聚合"，不必然被传染；
  - **但**：X-Pack（开放 API、RBAC、SSO）是商业许可，不适用上述结论。
- **结论：如果未来要卖"私有化部署包"，MaxKB 是负债不是资产。**

### 3.3 能力差距对本案的影响

| 能力 | 本案是否关键 | RAGFlow | MaxKB |
|---|---|---|---|
| 复杂 PDF（招股书、年报、处罚决定书扫描件） | **关键** | DeepDoc 内置 OCR + 版面分析 ✅ | 需外接 OCR ✅ |
| 跨页表格（财务报表、股权结构表） | **关键** | 有表格结构识别，跨页合并待验证 ⚠️ | 弱 ⚠️ |
| 按 `company_id` 过滤检索 | **关键** | 支持 `metadata_condition` ✅ | 需工作流封装 ⚠️ |
| 被 Flask 当纯检索接口调用 | **关键** | 原生支持 ✅ | 社区版不支持 ❌ |
| 对话式问答前端 | 次要 | 有 | **强项** |

### 3.4 结论

> **主用 RAGFlow，MaxKB 不引入。**
>
> 理由按权重排序：
> 1. **MaxKB 社区版没有平台 API**，无法满足"bettafish 通过 REST 检索"这个核心集成需求——这一条就否决了它；
> 2. RAGFlow 是 Apache-2.0，未来卖私有化部署包无法律负担；
> 3. 本案的文档以**复杂 PDF（年报、招股书、处罚决定书）**为主，DeepDoc 的 OCR + 表格识别是刚需，MaxKB 需额外采购 TextIn；
> 4. RAGFlow 的 `metadata_condition` 能把 `company_id` 写进文档元数据并做检索过滤，这是"实体对齐"落到检索层的关键。
>
> **例外**：如果后续要给业务人员一个"能对话的知识库助手"界面，可以单独买 MaxKB 专业版做前端，检索仍走 RAGFlow。但这是 P3 的事。

### 3.5 部署建议

```
RAGFlow 独立一台机器（或独立 docker compose）
  CPU 8C / 内存 16G / 磁盘 200G 起（文档原文+索引）
  vm.max_map_count >= 262144（用 Elasticsearch 时必须）
  如需扫描件 OCR 提速，再考虑 GPU（非必需）
```

⚠️ **待验证**：16G 是否够跑 ES + MySQL + MinIO + Redis + NATS + DeepDoc 全栈；官方推荐值是最低线，实际文档解析并发时会吃紧。建议首期按 32G 规划，或把 `DOC_ENGINE` 切到 Infinity 降内存（功能差异待验证）。

## 5. C. 实体对齐设计

> 这是全系统准确性的地基。做错这里，后面所有分析都是错的。

### 5.1 主键策略

**统一社会信用代码（USCC）作为公司唯一主键**，18 位，结构：

```
第 1 位     登记管理部门代码（9=工商）
第 2 位     机构类别代码
第 3-8 位   登记管理机关行政区划码
第 9-17 位  主体标识码（组织机构代码）
第 18 位    校验码（GB 32100-2015 定义的加权模 31）
```

- `uscc` 在 `kb.company` 上设 `UNIQUE`
- **入库前做校验位校验**，不合法直接拒绝（可过滤掉大量脏数据）
- 没有 USCC 的记录（如未上市公司新闻中提到的公司）进入 `kb.company_candidate` 待定表，**不直接写入 `company`**

### 5.2 名称归一化流水线

```text
原始名称
  │
  ├─① 字符归一化：全角→半角、繁→简、去空格、统一括号（（）→()）、去不可见字符
  │
  ├─② 精确匹配 kb.company.name            → 命中即结束（置信度 100）
  │
  ├─③ 精确匹配 kb.company_alias.norm_key  → 命中即结束（置信度 95）
  │
  ├─④ 规则剥离（谨慎，只用于生成候选）：
  │     · 去后缀：有限公司 / 股份有限公司 / 有限责任公司 / (中国)
  │     · 去地域前缀：北京市 / 上海 / 广东省…（仅用于召回，不作为合并依据）
  │
  ├─⑤ 相似召回：pg_trgm 三元组相似度 Top-20 + 名称向量 Top-20，取并集
  │
  ├─⑥ 特征加权打分：名称相似度 0.5 + 法人相同 0.2 + 注册地相同 0.15 + 成立时间接近 0.15
  │
  └─⑦ 分流：
        score >= 0.92 且 USCC 一致        → 自动合并
        0.75 <= score < 0.92             → 进人工复核队列
        score < 0.75                     → 视为新实体候选
```

**关键原则：模糊匹配只能"召回候选"，不能"自动合并"。** 自动合并的唯一充分条件是 USCC 一致。

### 5.3 同名不同主体

同名是常态（"华润置地（北京）有限公司"在多地都有）。区分依据按可靠性排序：

1. **USCC**（唯一可靠）
2. **（注册地 + 成立日期 + 法定代表人）三元组**
3. 注册资本 + 经营范围

**不允许**仅凭"名称完全相同"就合并。展示层必须始终带"注册地 + 成立年份"作为消歧后缀。

### 5.4 高管人物实体关联

**约束**：不采集身份证号 → 人物没有天然主键 → **人物实体天然是概率性的**。

处理策略：

1. 建立 `kb.person` 时只用 `(name_norm)` + 可选公开特征（性别、学历、公开履历关键词）
2. **人物与公司的关联通过 `employment` 表承载**，而不是把人物当作独立档案
3. 任职记录自带 `confidence`：
   - 工商公示直接给出"法定代表人" → 100
   - 上市公司公告"董事会决议聘任" → 95
   - 新闻中提及"XX 公司 CEO 张三" → 60（需二次源确认）
4. **同名人物的合并需人工确认**，系统只在 `kb.person_merge_candidate` 里给建议
5. 展示层：人物只作为"某公司的高管"出现，**不提供"某人的全部关联公司"视图**（这既是合规要求，也避免了同名误合并的连锁错误）

## 6. D. 存储与检索架构

### 6.1 职责边界

| 层 | 存什么 | 不存什么 | 为什么 |
|---|---|---|---|
| **PostgreSQL `kb` schema** | 结构化事实：公司、人物、任职、股权、事件、证据、财务、预警 | 文档全文、向量 | 需要事务、约束、JOIN、审计 |
| **RAGFlow（ES/Infinity）** | 文档 chunk 文本 + 向量 + 原文定位 | 结构化数值 | 需要混合检索与 rerank |
| **文件系统** | 原始 PDF/HTML、报告产物 | — | 证据原始件必须留档 |

### 6.2 两家怎么串起来

关键设计：**文档入库时把 `company_id` / `event_id` 写进 RAGFlow 的文档元数据**。

```text
采集到 PDF（如某公司 2024 年报）
   │
   ├─1. 落 kb.kb_document（doc_id, company_id, event_id, file_hash, source_url）
   │
   ├─2. 调 RAGFlow：POST /datasets/{id}/documents 上传
   │      并在 metadata 中写入 {"company_id": "...", "doc_type": "annual_report",
   │                              "doc_id": "...", "published_at": "..."}
   │
   ├─3. 轮询 parse_status → DONE，回写 kb.kb_document
   │
   └─4. 检索时：
        POST /api/v1/retrieval
        {
          "question": "该公司近三年被处罚情况",
          "dataset_ids": [...],
          "metadata_condition": {"company_id": "91310000XXXXXXXXXX"},
          "vector_similarity_weight": 0.3,   // 偏全文
          "top_k": 10
        }
        → 返回 chunks[] {content, similarity, document_id, document_name}
        → 用 document_id 反查 kb.kb_document → 拿到 source_url / published_at / company_id
        → 组装成 evidence（写 kb.evidence）
```

**这条链路是"可溯源"的物理实现**：报告里的每一句事实，都能沿着 `evidence_id → kb_document → source_url` 点回原始文件。

### 6.3 图查询：PG 递归 CTE vs Neo4j

| 需求 | 数据规模 | 推荐 | 依据 |
|---|---|---|---|
| 股权穿透（向上查实控人，向下降 3–5 层） | 单公司 < 1 万节点 | **PG 递归 CTE** | 固定深度、单一关系类型，`WITH RECURSIVE` 一次查询搞定；无需额外运维 |
| 关联方识别（同实控人、同高管、共同投资） | 中 | **PG + 闭包表物化** | 把穿透结果定期物化到 `kb.relation_closure`，查询变 O(1) |
| 事件传播链（报道 → 转载 → 官方回应） | 小 | **PG**（`event.parent_event_id`） | 本质是链表，不是图 |
| 动态路径枚举、社区发现、PageRank、多类型边加权最短路径 | 大 | Neo4j（P3 再评估） | 这些是 Cypher 的强项，SQL 表达极痛苦 |

**结论：P0–P2 一律用 PG，不引入 Neo4j。**

理由：
1. 你的查询模式是"固定几跳的穿透"，不是"任意深度探索"；
2. Neo4j 引入新的运维面（内存、备份、驱动、Cypher 学习成本），与 64G 单机的目标相悖；
3. 数据量级（几百万公司、几千万任职/股权边）PG 完全扛得住；
4. 只有当产品出现"给分析师一个图探索界面"的需求时，Neo4j 才划算。

**股权穿透 CTE 示例**

```sql
-- 向上穿透：查某公司的最终受益股东（最多 5 层，防环）
WITH RECURSIVE up AS (
    SELECT s.company_id, s.holder_company_id, s.holder_person_id,
           s.holder_name, s.ratio, 1 AS depth, ARRAY[s.company_id] AS path
    FROM kb.shareholder s
    WHERE s.company_id = :start_company_id
    UNION ALL
    SELECT s.company_id, s.holder_company_id, s.holder_person_id,
           s.holder_name, s.ratio, up.depth + 1,
           up.path || s.company_id
    FROM kb.shareholder s
    JOIN up ON s.company_id = up.holder_company_id
    WHERE up.depth < 5
      AND NOT s.company_id = ANY(up.path)   -- 防环
)
SELECT * FROM up ORDER BY depth, ratio DESC;
```

> 注意：`ratio` 逐层相乘得到"实际权益比例"，需在应用层计算；循环持股必须用 `path` 数组防死循环。

### 6.4 检索路由（查询进哪条路）

| 问题类型 | 走哪 | 例子 |
|---|---|---|
| 结构化事实（有几个股东、被罚几次、营收多少） | **PG SQL** | "这家公司实控人是谁" |
| 文档语义（年报里怎么说的、处罚理由是什么） | **RAGFlow 检索** | "年报里对海外风险的表述" |
| 混合（既要数字又要原文） | **两者并行 + LLM 合并** | "近三年被罚情况及其原因" |
| 时间序列（声量、情感趋势） | **PG 聚合** | "这个月负面声量走势" |

> **反模式**：不要把"公司注册资本"这类精确事实交给向量检索。向量检索擅长"意思相近"，不擅长"精确等于"。

### 7.4 事件时间线 / 声量曲线 / 情感拐点放哪？

**结论：放独立服务，不进 bettafish。**

| 理由 | 说明 |
|---|---|
| 计算性质不同 | bettafish 的循环是"LLM 生成文本"；声量/情感拐点是**统计计算**，用 SQL + numpy 即可，不需要 LLM |
| 会话绑定 | Streamlit 执行绑定浏览器会话，关页面就断，不适合定时/后台计算（架构文档 §1.2 已标注） |
| 可测试性 | 统计逻辑必须能单测（固定输入 → 固定输出），LLM 循环做不到 |
| 复用性 | 预警引擎需要每 15 分钟跑一次这些指标，不能每次都启动一个 Streamlit |

**建议形态**：一个 Python 包 `kb_analytics/`，纯函数 + CLI 入口，由 cron 或 APScheduler 调度；结果写 `kb.metric_daily` / `kb.event`。bettafish 只在**写报告时读取结果**。

## 8. F. 四个应用场景的落地方案

### 8.1 公司 / 高管背调

#### 8.1.1 评分卡维度设计

| 维度 | 权重 | 数据源 | 关键指标 | 取值逻辑 |
|---|---|---|---|---|
| 主体稳定性 | 15% | 工商 | 存续年限、经营异常次数、注册资本实缴率、法人变更频次（近 3 年） | 年限越长越高分；异常/频繁变更扣分 |
| 司法涉诉 | 20% | 裁判文书、执行公开 | 被执行人次数、失信记录、限高、涉诉案件数/金额 | 有失信直接 0 分 |
| 行政合规 | 15% | 信用中国、监管问询 | 行政处罚次数/金额、问询函数量 | 近 3 年处罚金额加权 |
| 财务健康 | 20% | 巨潮、Tushare | 营收增速、净利率、资产负债率、经营现金流 | 上市公司才能算；非上市标"数据缺失" |
| 舆情风险 | 15% | bettafish 采集 | 负面占比、情感均值、声量峰值、权威媒体负面 | 见 §8.2 指标 |
| 关联与股权 | 10% | 工商 | 股权集中度、对外投资数量、关联方风险传导 | 穿透后计算 |
| 资质与知产 | 5% | CNIPA、商标 | 专利数、商标数、经营资质 | 行业相对排名 |

**缺失维度处理**：按"可得维度权重之和"重新归一化，并在报告显著位置标注**数据覆盖率**（如 82%）。**不允许用默认值填充缺失维度**——那会制造虚假确定性。

#### 8.1.2 报告结构（12 章）

```
1. 摘要与结论（评分 + 3 条核心风险 + 数据覆盖率）
2. 主体基本信息（工商全量字段）
3. 股权结构与实际控制人（穿透图 + 穿透路径）
4. 高管团队（姓名/职务/任期 + 变更历史）
5. 司法涉诉（案件列表 + 金额 + 状态）
6. 行政处罚与监管措施
7. 财务表现（近 3 年，图表）
8. 经营活跃度（招投标中标、对外投资、资质）
9. 知识产权
10. 舆情态势（声量曲线 + 情感分布 + 关键事件）
11. 风险评级与建议
12. 证据附录（evidence_id → 来源 URL / 发布日期 / 原文摘录）
```

#### 8.1.3 高管背调（合规章节）

**只输出**：该高管在目标公司的**公开职务**、任期、历史任职（来自工商公示与公告）、公开披露的持股。
**不输出**：个人联系方式、住址、家庭成员、教育经历之外的私生活信息、其他不相关公司任职（避免人物画像）。

#### 8.1.4 如何保证事实可溯源（硬机制）

1. **LLM 输出契约**：所有事实句必须形如 `...（依据 E{evidence_id}）`；prompt 中明确"无证据的断言一律输出 `[数据不足]`"。
2. **后校验（关键）**：
   - 从报告中正则抽取所有 `E\d+`，校验 `evidence_id` 存在且指向的 evidence 的 `company_id` 与报告主体一致；
   - 抽取报告中的**数字 + 单位**（金额、次数、比例），回查 evidence 的 `quote` 是否包含该数字；不包含 → 标红并降级为"待核实"。
3. **渲染层**：`ReportEngine/renderers/html_renderer.py` 增加 evidence 角标，点击跳转 `source_url`。
4. **人工复核**：P0 阶段背调报告**必须先人工过一遍**再交付，同时把复核结果沉淀为评测集。

> 这一节是整个产品可信度的关键。**没有第 2 条的后校验，前面所有 RAG 都是装饰。**

### 8.2 事件来龙去脉

#### 8.2.1 事件表设计

已在 §5.5 给出 `kb.event`。补充两个关键设计：

- `cluster_key`：`event_type + 主公司 + 关键动作词归一` 的组合哈希，用于跨源去重
- `parent_event_id + relation_type`：构成事件链（`cause → progress → response → disposal → result`）

#### 8.2.2 多篇报道聚类成事件链

**四段式流水线**（全部是确定性算法，LLM 只在最后一步做命名）：

```text
① 文档级去重
   · URL 规范化（去 utm_*、去重定向参数、统一 www）
   · SimHash(64bit) 正文指纹，汉明距离 <= 3 判为重复
   · 同一 content_hash 直接丢弃

② 实体锚定
   · 抽取公司实体（用 kb.company_alias 做词典匹配，不依赖模型）
   · 抽取日期、金额、处罚文号等强特征
   · 无公司实体命中的报道 → 丢入待分类池

③ 语义聚类
   · embedding（复用 bettafish 已有的 sentence-transformers 或 RAGFlow embedding）
   · HDBSCAN / 层次聚类，cosine 阈值 0.82（需按语料调参）
   · 强约束：同一簇内 event_type 必须一致、公司一致、时间跨度 <= 30 天

④ 链化
   · 簇内按 published_at 排序
   · 相邻两条间隔 > 7 天 → 切分为不同事件
   · 用 relation_type 规则标注：
       - 首次出现 = cause
       - 官方回应（来源为政府/公司公告）= response
       - 处罚决定/判决 = result
   · LLM 只做：给每个事件起标题 + 写 100 字摘要（输入严格限定为该簇的 top-5 证据原文）
```

**关键判断**：**聚类判定不能交给 LLM**。LLM 聚类不稳定、不可复现、成本高。LLM 只在"命名与摘要"这一步，且输入必须封闭。

#### 8.2.3 趋势判断的量化指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 日声量 `volume_d` | 当日相关文档数 | 基础曲线 |
| 声量 z-score | `(x_d − μ_30d) / σ_30d` | 识别异常爆发（>2.5 视为异动） |
| 情感均值 `sent_d` | 当日情感分（−1…+1）加权平均 | 走向判断 |
| **情感拐点** | 对 `sent_d` 序列做 CUSUM 或 PELT 变点检测 | 定位"由正转负"的时刻 |
| 峰值滞后 | 峰值日 − 首报日 | 判断传播速度 |
| 半衰期 | 声量降至峰值 50% 所需天数 | 判断事件消退速度 |
| 来源结构 | 央媒/财经/地方/自媒体的占比 | 判断权威性与扩散层级 |
| 平台覆盖数 | 出现的平台数 | 判断扩散广度 |

> 全部是 SQL + numpy 可算的确定性指标，**不需要 LLM**，可单测、可回溯。

### 8.3 公关预警

#### 8.3.1 规则引擎设计

规则存 `kb.alert_rule.condition`（JSONB），示例：

```json
{
  "all": [
    {"metric": "negative_ratio", "window": "6h", "op": ">=", "value": 0.35},
    {"metric": "volume_zscore",  "window": "6h", "op": ">=", "value": 2.5},
    {"entity": "confidence", "op": ">=", "value": 0.80}
  ],
  "min_independent_sources": 2,
  "exclude": ["routine_announcement", "scheduled_report"]
}
```

**分级建议**

| 级别 | 触发场景 | 响应时限 | 通知方式 |
|---|---|---|---|
| **P0 紧急** | 央媒/监管点名、产品安全事故、高管涉案、股价异动叠加负面 | 30 分钟内 | 电话 + 企微 + 短信 |
| **P1 高** | 单平台声量 3σ 爆发且负面 > 50%、行政处罚公示 | 2 小时 | 企微 + 邮件 |
| **P2 中** | 负面占比抬升、单一媒体质疑 | 当日 | 日报汇总 |
| **P3 低** | 零星负面、竞品对比提及 | 每周 | 周报 |

#### 8.3.2 是否需要 ML

**P0–P2 不需要。** 规则 + 统计阈值即可覆盖 80% 场景，且**可解释**——这是预警系统最重要的属性，业务方要能问"为什么报这条"。

ML 只在 P3 引入，且只做**排序**不做**判定**：用历史误报/漏报反馈训练一个 small model，给候选告警打分排序，最终是否推送仍由规则决定。

#### 8.3.3 误报控制（五道闸）

1. **独立源门槛**：`min_independent_sources >= 2`，且必须来自不同域名
2. **权威源加权**：央媒/监管/交易所公告权重 3，财经媒体 2，自媒体 1；纯自媒体爆发不单独触发 P0
3. **实体置信度门槛**：`company.confidence >= 80`，否则只进观察池不发告警
4. **去重与静默期**：同一 `event_id` 24 小时内只告警一次；同一公司同类事件 6 小时静默
5. **白名单**：定期公告、财报预告、已报备的营销活动、已归档的旧事件

**误报反馈闭环**：`alert_record.status = false_positive` 时，把该 `(rule_id, 特征)` 记入 `kb.alert_false_positive`，供规则调参与 P3 训练。

### 8.4 应急预案

#### 8.4.1 预案库结构

```sql
CREATE TABLE kb.playbook (
    playbook_id   BIGSERIAL PRIMARY KEY,
    name          TEXT NOT NULL,
    event_type    TEXT NOT NULL,          -- 与 kb.event.event_type 对齐
    severity_min  SMALLINT,
    industry      TEXT,
    trigger_desc  TEXT,                   -- 什么情况下用
    owner_role    TEXT,                   -- 责任角色
    version       TEXT,
    updated_at    TIMESTAMPTZ
);

CREATE TABLE kb.playbook_step (
    step_id       BIGSERIAL PRIMARY KEY,
    playbook_id   BIGINT REFERENCES kb.playbook ON DELETE CASCADE,
    seq           INTEGER NOT NULL,
    phase         TEXT,                   -- 0-2h / 2-24h / 1-7d
    action        TEXT NOT NULL,
    owner_role    TEXT,
    deliverable   TEXT,                   -- 产出物（声明/通报/客服话术）
    sla_hours     NUMERIC(5,1)
);
```

#### 8.4.2 触发后如何生成处置建议

```text
① 事件定级（规则引擎 → severity + event_type + industry）

② 双路召回
   A. 结构化：SELECT 相似历史案例
      WHERE event_type 相同 AND severity >= 当前级别-1 AND industry 相近
      ORDER BY 时间衰减
   B. 语义：RAGFlow 检索"事件描述"在 playbook 库与历史案例库中的 top-k

③ 合并去重 → 取 top-5 相似案例

④ LLM 生成建议，**强约束**：
   · 输入只给：当前事件事实（带 evidence）+ top-5 案例 + 命中的 playbook 步骤
   · 输出必须引用案例 id 与 playbook step id
   · 禁止生成输入中不存在的事实

⑤ 输出结构
   1) 事件定性与分级依据
   2) 建议响应时间窗（0-2h / 2-24h / 1-7d）
   3) 处置动作清单（来自 playbook + 相似案例补充）
   4) 对外口径要点（3 条以内）
   5) 相似历史案例（含最终结果，供参考）
   6) 待人工确认项
```

> **关键**：应急预案的价值在于"**动作清单**"而不是"LLM 写的漂亮话"。所以 playbook 必须是业务方维护的结构化数据，LLM 只做匹配与归纳。

## 10. 需要用户决策的开放问题

1. **数据预算**：天眼查/企查查/剑鱼/Tushare 的年度采购预算上限是多少？这直接决定 P0 是"买确定性"还是"写爬虫"。
2. **交付形态**：这套系统只内部自用，还是要**交付镜像给客户私有化部署**？（若是后者，MaxKB 的方案彻底出局，且 RAGFlow 也不能用其商标宣传）
3. **知识库规模**：预计入库文档量级是 1 万份还是 100 万份？是否需要处理大量扫描件？（决定 RAGFlow 是 32G 单机还是要上 GPU/多节点）
4. **预警时效**：P0 级告警要求多久内送达——30 分钟、2 小时还是次日？（决定是否需要实时流，还是每 15 分钟批处理即可）
5. **用户规模**：是 3–5 个分析师自用，还是要开放给几十人？（决定 P3 的多用户与权限是否要提前到 P1）
6. **与 bettafish 的关系**：未来是保留它的完整舆情面板（三引擎 + iframe），还是只把它当"报告生成后端"？（这决定要不要先做架构文档里的 iframe 改造）
