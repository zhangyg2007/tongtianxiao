## 0. 一页摘要

**这个系统是什么**：一个**单机部署的舆情分析工作台**。用户输入一个主题，系统让三个分析引擎并行跑出三份素材报告（全网调研 / 多模态图文 / 本地数据库深度分析），再由报告引擎汇总成一份带章节结构的长报告，支持 HTML / Markdown / PDF 导出。

**架构一句话**：`1 个 Flask 主应用（:8080）+ 3 个独立 Streamlit 子进程（:8501/:8502/:8503）+ 1 个 PostgreSQL`。ReportEngine 以 Blueprint 形式跑在主应用进程内；ForumEngine 是主应用内的后台线程；MindSpider 是独立的命令行采集工具。

**三个最重要的架构判断**：

1. **引擎之间没有 API 调用，靠"约定目录 + 文件时间戳"隐式协作**。ReportEngine 判断"输入是否就绪"的方式是扫描三个引擎的输出目录里有没有**新增的 `.md`**（`ReportEngine/agent.py:135-169`、`1602-1661`），并通过检查 `logs/forum.log` 是否存在来决定能不能出报告（`ReportEngine/agent.py:1602-1661`）。这意味着"主链路是否跑通"完全取决于文件是否落盘，任何一个引擎没产出 `.md`，报告就会被 400 拒绝（`ReportEngine/flask_interface.py:653-660`）。
2. **前端不是 SPA，而是"单页 + 三个 iframe 直连 Streamlit 端口"**。引擎的启动与查询完全靠 URL 参数 `?query=...&auto_search=true` 驱动（`templates/index.html:2280-2282`、`3342`、`3356`），Streamlit 必须能被浏览器直接访问，**不是纯后端 API 调用**。这是后续做对外服务化/反向代理时最大的改造点。
3. **四个引擎是"同一模板复制四份"**：都有 `llms/base.py`、`prompts/prompts.py`、`nodes/`、`state/`、`tools/`、`utils/` 的相同结构，四个 `llms/base.py` 内容几乎一致（各自约 6KB、MD5 不同），**没有共享基类**。好处是互不干扰，坏处是改一处要改四处。

**当前主要短板**：无鉴权、`/api/config` 明文回传全部密钥、无进程守护、报告任务全局单例串行、InsightEngine 参数导致单次分析耗时以小时计。

## 1. 当前服务的主要功能

### 1.1 端到端业务流程（业务语言）

1. **运营人员在前端输入一个分析主题**（例如"比亚迪 新能源汽车 舆情"）。
2. **点"开始搜索"**：前端把主题拼进三个 iframe 的 URL，浏览器分别打开三个 Streamlit 页面（`:8503` Query、`:8502` Media、`:8501` Insight），每个页面带 `auto_search=true`，打开即自动开始（`SingleEngineApp/*_streamlit_app.py` 中 `st.query_params` 读取逻辑）。
3. **三个引擎各自独立工作，产出各自的报告文件**：
   - **QueryEngine（全网调研）**：联网检索（Tavily）→ 大模型按"章节-反思"循环写成 5 段式调研报告 → 落 `query_engine_streamlit_reports/deep_search_report_<主题>_<时间戳>.md`。
   - **MediaEngine（多模态）**：调用多模态搜索（Anspire 或 Bocha）拿图文卡片 → 大模型整理成多模态舆情报告 → 落 `media_engine_streamlit_reports/*.md`。
   - **InsightEngine（本地库深挖）**：查询本地 PostgreSQL 中已爬取的 7 个平台数据 → 关键词优化 → 逐段"搜索-反思-总结" → 落 `insight_engine_streamlit_reports/*.md`。
4. **运营点"生成报告"**：前端调用 `POST /api/report/generate`（`templates/index.html:6110`），ReportEngine 先做"输入就绪"门禁检查，通过后在**后台线程**里生成结构化长报告（章节 JSON → 整本 IR → HTML），并通过 SSE 推送进度与日志。
5. **产出报告**：HTML / Markdown / PDF 落到 `final_reports/`，前端内嵌预览。
6. **ForumEngine（AI 主持人）全程旁听**：后台线程持续读取各引擎日志，生成"主持人点评"写入 `logs/forum.log`，作为报告素材与门禁条件之一。

### 1.2 用户实际操作路径（点击次数 / 等待时长 / 可见反馈）

| 步骤 | 操作 | 典型耗时（实测/估算） | 用户能看到什么 |
|---|---|---|---|
| 1 | 打开 `http://<host>:8080/` | 1–3s | 主界面：主题输入框 + 三个引擎面板（iframe） |
| 2 | 首次进入时启动引擎（前端触发 `POST /api/system/start`） | 30–60s（三个 Streamlit 依次启动，每个最多等 30s） | 面板从"未启动"变为引擎页面 |
| 3 | 输入主题，点"开始搜索"（1 次点击） | — | 三个面板同时开始滚动日志 |
| 4 | 等待 Query / Media 完成 | **约 5 分钟**（实测，见 1.4） | 面板内最终显示 Markdown 报告 |
| 5 | 等待 Insight 完成 | **约 20 分钟才到 2/5 段**（实测，默认参数下全流程可能 > 1 小时） | 进度条 + 当前段落标题 |
| 6 | 点"生成报告"（1 次点击） | 估算 3–8 分钟 | SSE 日志流 + 进度百分比 |
| 7 | 查看/下载报告 | 立即 | HTML 预览、Markdown、PDF 下载按钮 |

> 注意：**三个引擎是浏览器直连的 Streamlit 会话**，关闭标签页会中断引擎执行（Streamlit 脚本运行绑定会话）。这一点对"后台批处理"场景不友好。

### 1.3 功能模块矩阵

| 模块 | 解决什么问题 | 输入 | 输出 | 产物位置 | 主链路/可选 |
|---|---|---|---|---|---|
| **SingleEngineApp / QueryEngine** | 全网公开信息调研（不依赖本地库） | 主题字符串 + Tavily Key | 5 段式 Markdown 调研报告 + 研究状态 JSON | `query_engine_streamlit_reports/` | **必需** |
| **SingleEngineApp / MediaEngine** | 图文/视频多模态舆情素材整理 | 主题 + 多模态搜索 Key（Anspire/Bocha）+ LLM Key | 多模态 Markdown 报告 + 状态 JSON | `media_engine_streamlit_reports/` | **必需**（报告门禁要求） |
| **SingleEngineApp / InsightEngine** | 对**本地已爬取**的多平台数据做深度分析 | 主题 + 本地 PostgreSQL + LLM Key | 深度分析 Markdown + 状态 JSON | `insight_engine_streamlit_reports/` | **必需**（报告门禁要求） |
| **ReportEngine** | 把三份素材汇总为结构化长报告 | 三份 `.md` + `logs/forum.log` + 主题/模板 | 章节 JSON → 整本 IR → HTML/MD/PDF | `final_reports/`（`html/`、`md/`、`ir/`、`chapters/`、`pdf/`） | **必需** |

| **MindSpider** | 采集 7 个社媒平台数据入本地库 | 关键词/日期、平台账号 Cookie | 数据库记录（笔记/视频/评论） | PostgreSQL 表 | **可选**（只有在需要本地库数据时才跑） |
| **SentimentAnalysisModel** | 对检索结果做情感打标/聚类 | 文本 | 情感标签、聚类结果 | 内存（无独立产物） | **可选增强**（默认启用，可关） |
| **Flask 主应用 `app.py`** | 统一入口：页面、配置、启停、状态、Socket.IO | HTTP / WebSocket | 页面、JSON、日志推送 | — | **必需** |

### 1.5 必需主链路 vs 可选增强

**必需主链路（缺一不可出报告）**
- QueryEngine + MediaEngine + InsightEngine 三者各产出一份**新的** `.md`
- `logs/forum.log` 存在
- ReportEngine 生成成功

**可选增强（不影响"能否出报告"，但影响质量/覆盖）**
- **MindSpider 爬虫**：只在"需要本地库有数据"时才跑；InsightEngine 的数据完全来自本地库，库空则 Insight 报告内容空洞。
- **SentimentAnalysisModel**：默认启用（`InsightEngine/tools/sentiment_analyzer.py:32`），但**首次使用会联网下载 HuggingFace 模型**；模型不可用时异常被捕获、自动降级（不影响主流程）。
- **ForumEngine**：严格说是"弱必需"——报告门禁只检查 `logs/forum.log` 是否存在，不检查内容。
- **GraphRAG 图谱视图**：`/api/graph*` 与 `graph-viewer` 页面（`app.py:1313`、`1446`、`1462`），独立于报告主链路，纯展示。

## 2. 技术架构

### 2.1 技术栈清单

| 层 | 选型 | 用在哪 | 为什么这么选（代码/文档依据） |
|---|---|---|---|
| Web 框架 | **Flask 2.3.3 + Flask-SocketIO + eventlet** | 主应用 :8080 | 需要页面 + 长任务进度推送，Socket.IO 用于把日志实时推到前端（`app.py` 顶部、`_patch_eventlet_disconnect_logging`） |
| 引擎 UI | **Streamlit 1.28.1（×3，独立进程）** | :8501/:8502/:8503 | 直接复用 Streamlit 的"脚本即页面"能力，省掉前端开发；代价是只能通过浏览器会话驱动 |
| 任务调度 | **同步脚本 + 子进程 + 后台线程**（无队列） | Streamlit 进程内同步执行；ReportEngine 用 `threading.Thread`（`ReportEngine/flask_interface.py:664-676`）；引擎用 `subprocess.Popen`（`app.py:645-697`） | 单机单用户场景，未引入 Celery/Redis |
| LLM 接入 | **OpenAI Python SDK + `base_url` 兼容协议** | 四个引擎各一份 `llms/base.py` | 统一走 OpenAI 兼容接口，因此 DeepSeek / Kimi / 通义 / 豆包等只要兼容就能换（详见 3.1） |
| 数据存储 | **PostgreSQL（默认）/ MySQL / SQLite 可切**，SQLAlchemy + 原生 SQL 混用 | 爬虫写入、Insight 查询、报告状态 | `DB_DIALECT` 配置；`deploy/init_db.sql` + 23 张表 |
| 缓存 | **无强依赖**（MediaCrawler 内置可选 Redis 缓存） | 仅爬虫代理/短信缓存 | 当前配置未启用，**Redis 可以不装**（见 2.5） |
| 前端 | **原生 HTML/CSS/JS 单页 + 三个 iframe + Socket.IO** | `templates/index.html`（约 3500 行） | 无构建步骤、无框架，部署简单；代价是端口硬编码、无组件化 |
| 报告渲染 | **自定义 IR（中间表示）→ HTML 字符串渲染 → WeasyPrint 出 PDF** | `ReportEngine/renderers/html_renderer.py`（约 370KB）、`ReportEngine/scripts/export_to_pdf.py` | IR 让"同一份内容多端渲染"成为可能（HTML/MD/PDF） |
| 报告模板 | **6 套内置 Markdown 模板 + 支持自定义模板** | `ReportEngine/report_template/`（企业品牌声誉、市场竞争格局、日常监测、政策行业、社会公共热点、突发事件危机公关） | `POST /api/report/generate` 接受 `custom_template`（`ReportEngine/flask_interface.py:621-696`） |
| 爬虫 | **Playwright + MediaCrawler（7 平台）** | `MindSpider/DeepSentimentCrawling/` | 复用开源 MediaCrawler，Playwright 驱动真实浏览器过反爬 |
| 配置 | **pydantic-settings + `.env`** | 根 `config.py`（`Settings(BaseSettings)`，`config.py:111` 指定 env_file） | 环境变量优先，便于容器化 |
| 日志 | **loguru + 文件日志 + Socket.IO 推送** | `logs/*.log` | 多引擎日志分文件，便于 ForumEngine 旁听 |

**进程模型要点**

| 进程/线程 | 端口 | 由谁拉起 | 生命周期 |
|---|---|---|---|
| Flask 主应用 | 8080（`HOST`/`PORT` 来自 `.env`，`app.py:1607-1618`） | 手动/脚本 | 常驻 |
| InsightEngine Streamlit | 8501（`app.py:511-514`） | `POST /api/system/start` → `initialize_system_components()` → `subprocess.Popen`（`app.py:297-311`、`645-697`） | 跟随主应用启停 |
| MediaEngine Streamlit | 8502 | 同上 | 同上 |
| QueryEngine Streamlit | 8503 | 同上 | 同上 |
| ReportEngine | 无独立端口 | 主应用 Blueprint（`app.py:78-83`），任务跑在线程里 | 跟随主应用 |
| ForumEngine | 无端口 | 主应用内后台监控线程（`app.py:370-396`） | 跟随主应用 |
| MindSpider | 无 | **手动命令行**，主应用只在启动时调 `initialize_database()`（`app.py:26`、`277-348`） | 一次性 |

> 关键细节：`start_streamlit_app()` **没有传 `--server.address`**（`app.py:645-697`），所以三个 Streamlit 默认监听 `0.0.0.0`；如果服务器安全组把 8501–8503 暴露公网，等于三个无鉴权的分析页面直接对外开放。云上验证环境只放行了 8080，所以侥幸没暴露。

### 2.4 数据持久化

**PostgreSQL 表（共 26 张）**

| 分组 | 表 | 用途 |
|---|---|---|
| 采集数据（7 平台，来自 `MindSpider/DeepSentimentCrawling/MediaCrawler/schema/tables.sql`） | `weibo_note`、`xhs_note`、`douyin_aweme`、`kuaishou_video`、`bilibili_video`、`tieba_note`、`zhihu_content` | 主贴/视频内容 |
| 评论（7 张） | `weibo_note_comment`、`xhs_note_comment`、`douyin_aweme_comment`、`kuaishou_video_comment`、`bilibili_video_comment`、`tieba_comment`、`zhihu_comment` | 评论内容 |
| 辅助（8 张） | 各平台的作者/创作者表等 | 账号元数据 |
| 话题（4 张，`MindSpider/schema/mindspider_tables.sql`） | `daily_news`、`daily_topics`、`topic_news_relation`、`topic_summary` | 每日新闻 → 话题抽取 → 话题-新闻关联 → 话题摘要 |
| 预留（M2） | `corpus_embeddings`（`deploy/init_db.sql`） | 向量检索预留 |

**pgvector 的真实情况（重要澄清）**
- `deploy/init_db.sql` 里确实执行了 `CREATE EXTENSION IF NOT EXISTS vector;` 并建了 `corpus_embeddings` 表。
- **但当前代码没有任何地方读写向量表**（全仓库检索 `pgvector|vector(|embedding` 只命中情感模型的注释与训练脚本）。
- 结论：**pgvector 目前是"装了但没用"的前瞻性设计**，属于可选安装；不装也不影响现有链路（只是 `init_db.sql` 会执行失败，需要跳过该段）。

**Redis**
- 项目主流程不依赖 Redis。Redis 只出现在 MediaCrawler 的**可选缓存后端**（代理池/短信验证码缓存），默认走本地内存缓存。
- 结论：**Redis 可以不装**。

**报告文件组织**
- 一次分析 = 1 份 HTML + 1 份状态 JSON + 1 份 IR + N 份章节 JSON；MD/PDF 为按需导出。
- 报告引擎自带"基线文件"`logs/report_baseline.json`，用于判断"哪些文件是本次新增"（`ReportEngine/agent.py:98`、`130`）。

### 2.5 关键抽象与耦合点

**LLM 客户端：有统一协议，但没有统一代码**

| 项 | 现状 | 证据 |
|---|---|---|
| 协议 | 全部基于 `openai.OpenAI(base_url=..., api_key=...)` | 四个 `llms/base.py` 里的 `OpenAI(` 调用 |
| 代码复用 | **4 份各自独立的 `LLMClient` 类**，文件大小接近、MD5 不同 | `QueryEngine/llms/base.py`、`MediaEngine/llms/base.py`、`InsightEngine/llms/base.py`、`ReportEngine/llms/base.py` |
| 超时 | Insight 默认 1800s；Report 3000s；均可用 `LLM_REQUEST_TIMEOUT` 覆盖 | `InsightEngine/llms/base.py:43-47`、`ReportEngine/llms/base.py:54-58` |
| 重试 | 全局 `LLM_RETRY_CONFIG`：**6 次重试、首次等 60s、指数退避、单次最长 600s** | `utils/retry_helper.py:228-233` |
| Prompt 位置 | 每个引擎自己的 `prompts/prompts.py`（按引擎拆分，无集中管理） | `{Query,Media,Insight,Report}Engine/prompts/prompts.py` |

**配置注入**
- 唯一配置源：根 `config.py` 的 `Settings(BaseSettings)`，读 `.env`（`config.py:111`）。
- **引擎自己的 `Settings` 类不读 `.env`**（`InsightEngine/utils/config.py` 无 `env_file`），必须由 Streamlit 应用把根配置的值显式传进去（`SingleEngineApp/insight_engine_streamlit_app.py:110-128`）。这意味着**引擎无法独立命令行启动**，必须走 Streamlit 或自己写装配脚本。

**硬编码耦合（部署/改造时的雷区）**

| 耦合点 | 位置 | 影响 |
|---|---|---|
| 三个 Streamlit 端口写死 8501/8502/8503 | `app.py:511-514`、`templates/index.html:2280-2282`、`3342` | 改端口要同时改前后端；反向代理必须按这三个端口转发 |
| iframe 用 `location.hostname + :端口` 直连 | `templates/index.html:3356` | 只支持"同机直连"，无法走统一域名/子路径；HTTPS 下会混合内容报错 |
| ReportEngine 靠"目录里有没有新 `.md`"判断就绪 | `ReportEngine/agent.py:135-169` | 任何残留/误写文件都会误判；并发任务会互相污染 |
| 报告任务全局单例 `current_task` | `ReportEngine/flask_interface.py`（模块级 `current_task` + `task_lock`） | 同一时刻只能跑一个报告任务 |
| 引擎输出目录名写死 | 各 Streamlit 应用 `OUTPUT_DIR` | 改目录要同步改门禁代码 |
| 遗留 `/api/search` 指向 8601/8602/8603 | `app.py:1145-1191` | 三个端口根本不存在，此接口是**死代码**，误用会 500/超时 |

| # | 问题 | 证据 | 严重程度 | 影响 |
|---|---|---|---|---|

## 3. 可扩展的服务方向

> 说明：以下判断均从**代码里真实存在的扩展点**出发；"改动量"按单人工作量粗分：小 = 1 天内，中 = 3–5 天，大 = 1–2 周以上。

### 3.1 LLM 供应商替换与多模型路由

**现状**：四个引擎都走 OpenAI 兼容协议，配置项是 `*_ENGINE_BASE_URL / API_KEY / MODEL_NAME`。云机验证时已实测：把 MediaEngine 从 Gemini（aihubmix）切到 DeepSeek，**只改 `.env` 四行就生效**，代码零改动。

**扩展判断**

| 目标 | 改动量 | 涉及文件 | 风险 |
|---|---|---|---|
| 接一家新的 OpenAI 兼容国产模型（豆包/通义/智谱/百川） | **小**（只改 `.env`） | `.env`；`config.py` 的 `CONFIG_KEYS` | 模型名/上下文长度差异；部分厂商不支持 `response_format` |
| 同一引擎按任务混用多模型（如"规划用强模型、总结用便宜模型"） | **中** | 各引擎 `llms/base.py`（增加模型路由函数）、`nodes/*.py` 调用点 | 四个引擎各改一遍；成本/质量需回归 |
| 全局统一 LLM 客户端（消除四份拷贝） | **中** | 新建 `common/llm_client.py`，四个 `llms/base.py` 改为薄封装 | 四引擎超时/重试语义不一致，需要统一 |
| 支持非 OpenAI 协议（Claude/原生 Gemini） | **中** | 只需扩展一个 client 类 + 适配层 | 消息格式/多模态字段差异 |

**关键判断**：**"换供应商"是低成本操作，"多模型混用"才是真正需要开发的点**。建议先做配置化（已完成），再视成本压力做路由。

### 3.2 数据源扩展（爬虫平台）

**现状**：`MindSpider/DeepSentimentCrawling/MediaCrawler/media_platform/` 下已有 **7 个平台**：`weibo`、`xhs`、`douyin`、`kuaishou`、`bilibili`、`tieba`、`zhihu`。每个平台固定三件套：`core.py`（爬取流程）、`client.py`（接口封装）、`login.py`（登录态），共享 `base/base_crawler.py` 抽象基类与 `store/` 落库层。

**扩展判断**

| 目标 | 改动量 | 涉及文件 | 风险 |
|---|---|---|---|
| 新增一个已支持形态的平台（如快手/贴吧之外的同类） | **中**（3–5 天） | `media_platform/<new>/{core,client,login}.py` + `database/models.py` 加表 + `store` 落库分支 | 反爬强度差异大；登录态（Cookie/扫码）在服务器上难维护 |
| 新增一个"非笔记/视频"形态（如新闻站、论坛） | **中偏大** | 同上 + `InsightEngine/tools/search.py` 加表映射与字段映射 | Insight 查询逻辑按平台写死字段（`search.py:259-262`），新平台要同步改 |
| 抽象出统一"采集接口"给第三方数据源（API 取代爬虫） | **大** | 新建采集适配层；`MindSpider` 改为调用适配器 | 现有代码强依赖 MediaCrawler 的表结构 |

**关键判断**：**加平台不是"加个文件"，而是"加文件 + 加表 + 加 Insight 字段映射"三处联动**。真正省事的做法是先把 `InsightEngine/tools/search.py` 的平台字段映射配置化。

### 3.3 分析能力扩展

| 能力 | 现状 | 改动量 | 接入位置 | 风险 |
|---|---|---|---|---|
| 情感分析换成 API（火山/阿里） | 本地 BERT 模型，默认联网下载（`sentiment_analyzer.py`） | **小** | `InsightEngine/tools/sentiment_analyzer.py` 的 `analyze_batch` | 批量调用成本；限流 |
| 实体识别（人名/机构/产品） | 无 | **小–中** | 新增 `InsightEngine/tools/entity_extractor.py`，在 `_initial_search_and_summary` 后调用 | 需要定义实体 schema 并写入报告章节 |
| 事件聚类/话题演化 | 有 `ENABLE_CLUSTERING`（SentenceTransformer） | **中** | `InsightEngine/agent.py:32-36`、`_get_clustering_model()` | 现有实现依赖本地 embeddings，换 API 需重写相似度计算 |
| 趋势预测/时间序列 | 无 | **大** | 新增独立分析服务 + 新报告章节模板 | 数据密度要求高（需要历史时间序列） |

**关键判断**：**情感分析换 API 是性价比最高的"能力升级"**——它同时解决"内网无法下载 HF 模型"和"Insight 启动慢"两个问题。

### 3.4 报告与输出扩展

| 目标 | 改动量 | 涉及文件 | 风险 |
|---|---|---|---|
| 新增报告模板 | **小** | `ReportEngine/report_template/*.md` + 模板选择逻辑 | 模板变量与 IR 结构需匹配 |
| 自定义模板（用户上传） | **已支持** | `POST /api/report/generate` 的 `custom_template`（`flask_interface.py:621-696`） | 模板注入/XSS 需过滤 |
| 输出 Word | **中** | 新增 renderer（python-docx），复用 IR | 排版与 HTML 不一致 |
| 输出 PPT | **中偏大** | 新增 renderer（python-pptx），需要"章节→页"映射 | 版式设计工作量大 |
| 输出飞书文档 | **中** | 新增 exporter，调用飞书开放平台 | 需要企业自建应用与权限申请 |
| 定时生成 | **中** | 新增调度器（APScheduler），复用 `POST /api/report/generate` 内部函数 | 门禁依赖"新增文件"，定时任务需先清空基线 |

**关键判断**：报告层是全项目**抽象最干净的一层**（IR 中间表示），加输出格式的成本主要在"版式"而不在"数据"。**Word/飞书优先级应高于 PPT**。

### 3.5 任务与调度扩展

| 目标 | 改动量 | 涉及文件 | 风险 |
|---|---|---|---|
| 多任务并发（报告） | **中** | `flask_interface.py`：`current_task` 单例 → 任务表 + 并发控制 | 引擎目录共享，会互相污染（需按任务隔离目录） |
| 任务持久化/断点续跑 | **中** | 已有 `report_state_*.json`，补"启动时恢复" | 状态与文件可能不一致 |
| 队列化（Celery/RQ + Redis） | **大** | 报告任务与引擎任务全部改造 | 引入 Redis 与 worker 运维成本 |
| 定时任务 | **中** | APScheduler + 任务表 | 与"文件门禁"机制冲突 |

**关键判断**：**并发的前置条件是"目录隔离"**，不解决 `*_engine_streamlit_reports` 共享目录，做队列只会放大问题。

### 3.6 多用户与权限

**现状**：完全无鉴权；`/api/config` 明文回传密钥；Streamlit 端口无保护。

| 目标 | 改动量 | 涉及文件 | 风险 |
|---|---|---|---|
| 基础登录（账号密码 + Session） | **小–中** | `app.py` 增加 `before_request` + 登录页 | Streamlit iframe 无法带 Cookie 校验（跨端口），需改为反向代理统一域名 |
| 多租户隔离（每人独立任务/目录） | **大** | 报告任务、引擎目录、配置全部按用户隔离 | 与现有"全局单例 + 共享目录"架构冲突最大 |
| API Key 鉴权（对外接口） | **小** | `before_request` 校验 header | 需要密钥轮换机制 |

**关键判断**：**"能加登录"容易，"能多租户"很难**——因为端口直连 iframe 与共享输出目录这两个设计，决定了它天然是"单机单用户"架构。

### 3.7 对外服务化（REST API）

**现状**：ReportEngine 已经是标准 REST + SSE（14 个路由，`ReportEngine/flask_interface.py`），可以直接被第三方调用；但**引擎触发没有 API**——只能靠浏览器打开 iframe。

| 目标 | 改动量 | 涉及文件 | 风险 |
|---|---|---|---|
| 报告生成对外 API | **小** | 已有 `/api/report/generate` + `/stream` + `/download`，补鉴权即可 | 需先解锁"输入就绪"门禁（依赖文件） |
| 引擎触发 API | **中–大** | 需要把 Streamlit 逻辑抽成可调用服务（或 Playwright 驱动，不推荐） | Streamlit 会话模型与 API 模型天然不兼容 |
| 统一网关（单端口对外） | **中** | Nginx 反代 8080 + 8501-8503 + 子路径重写 | Streamlit 对子路径支持差（需 `--server.baseUrlPath`） |

**关键判断**：**报告层可以先对外，引擎层不适合直接对外**。若要做开放平台，建议把三个引擎重写为"无 Streamlit 的后端服务"，这是大改造。

## 4. 定制方向建议（按投入产出排序）

### ① 安全加固 + 部署形态标准化（投入小，收益极大）⭐ 最优先
- **做什么**：加统一鉴权（最简单是 Nginx Basic Auth 或 `before_request` + 会话）；`/api/config` 改为"只回传是否已配置（true/false）"，密钥永不回显；给 8080/8501-8503 做反向代理收口到单端口 + HTTPS；给主应用加 systemd 守护。
- **为什么先做**：当前**任何能访问 8080 的人都能拿到全部 API Key 并启停服务**（`app.py:1194-1203`）。上本地服务器后一旦开放给同事，这是不可接受的风险。
- **改动量**：小（1–2 天）。

### ② InsightEngine 参数化调优（投入小，收益立竿见影）
- **做什么**：`MAX_REFLECTIONS` 3→1、`MAX_PARAGRAPHS` 6→4、`MAX_CONTENT_LENGTH` 500000→20000、关闭 `ENABLE_CLUSTERING` 与默认情感分析、收紧 `LLM_RETRY_CONFIG`（6 次/60s → 2 次/5s）。
- **为什么先做**：实测 20 分钟只到 2/5 段（`InsightEngine/utils/config.py:25-28`、`SingleEngineApp/insight_engine_streamlit_app.py:63-64`）。这些参数不调，**换再好的服务器也快不起来**——瓶颈是"超长 prompt + 重试等待"，不是 CPU。
- **改动量**：小（半天到 1 天，含验证）。

### ③ 引擎触发服务化（去掉 iframe 依赖）（投入中，收益大）
- **做什么**：把三个 Streamlit 应用的"业务执行部分"抽成可被 Flask 调用的函数/子进程任务（保留 Streamlit 作为可选 UI），前端改为轮询/SSE 获取进度；输出目录按任务 ID 隔离。
- **为什么值得做**：这是**所有后续扩展（队列、并发、多用户、对外 API）的共同前置条件**。iframe + 端口直连 + 共享目录这套组合，正在阻止上面每一项能力落地。
- **改动量**：中（5–8 天）。

### ④ 报告层输出扩展（Word / 飞书）（投入中，收益直接）
- **做什么**：基于现有 IR 新增 `docx_renderer` 与飞书 exporter；模板继续用 Markdown。
- **为什么值得做**：IR 抽象已经就绪（`ReportEngine/renderers/`），加格式只写渲染器；业务方对"能直接发 Word/飞书"的诉求通常比"多一个分析算法"更强烈。
- **改动量**：中（3–5 天）。

### ⑤ 分析能力升级：情感分析 API 化 + 实体识别（投入小–中，收益中）
- **做什么**：把本地 BERT 情感模型替换为火山/阿里情感 API；新增实体识别节点并写入报告章节。
- **为什么值得做**：同时解决"内网下不了 HF 模型"和"Insight 启动慢"两个现实问题（`InsightEngine/tools/sentiment_analyzer.py:32`、`agent.py:14`），并且实体识别是舆情报告里最容易体现"专业度"的增量。
- **改动量**：小–中（2–4 天）。

> **不建议现在做**：多租户、Celery 队列、PPT 导出、爬虫平台大扩。前三者都依赖 ②③ 完成，最后一项维护成本（登录态/反爬）远高于收益。
