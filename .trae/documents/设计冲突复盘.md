## 一、还原两条设计线

### 1.1 A 线：M2「多用户业务层」

**业务目标（推断依据：`server/app/models.py:31` 的类注释、`server/app/pipeline.py:1-9` 的模块文档、`web/src/router/index.ts` 路由）**

把 BettaFish 从"单机单用户分析工具"包一层业务壳：用户注册登录 → 提交分析任务 → 后台管线驱动基座 → 产出报告索引 → 报告/配置管理。**核心假设是"基座不动"**。

| 任务管理 | **无队列**：FastAPI `BackgroundTasks` + 后台线程轮询基座 HTTP；状态 `pending→running→reporting→completed/failed` 落在自己的 `analysis_tasks` 表 | [tasks.py:30-41](file:///d:/WORKSPACE/TraeWorkspace/bettafish-main/server/app/routers/tasks.py#L30-L41)、[pipeline.py:28-101](file:///d:/WORKSPACE/TraeWorkspace/bettafish-main/server/app/pipeline.py#L28-L101) |

**设计前提**（决定了它为什么会被 P0 推翻）：

1. 基座**无任务态**——所以 A 线自己造任务表、自己轮询（`pipeline.py:3-6` 明说）。
2. 基座**同一时刻只能跑一个报告任务**——`pipeline.py:51-52` 注释："基座同一时刻只允许一个报告任务（冲突也返回 400），统一按可重试处理"。
3. 产物是**目录里的文件**——`Report` 只存 `file_path/pdf_path/md_path`，正文不解析（`models.py:46-58`）。

**交付程度：半成品 / 断链** ✅

- `server/`：代码结构完整、有 2 个测试文件，能独立起服务；但它只是一个**代理层**，没有改造基座。
- `web/`：路由声明了 `/reports`、`/report/:id`、`/config` 三个页面，但 [router/index.ts:27-40](file:///d:/WORKSPACE/TraeWorkspace/bettafish-main/web/src/router/index.ts#L27-L40) 引用的 `ReportsView.vue`、`ReportDetailView.vue`、`ConfigView.vue` **在 `web/src/views/` 下不存在**（实际只有 Home/Login/Register/Analysis）。
- `web/` 的 API 基址是 `http://localhost:5000/api`，而 A 线自己的后端在 8000 → **管理端从第一天起就打不通**（`web/src/utils/http.ts:5`）。
- `wxapp/`：`app.json` 声明 7 页，实际只有 `pages/index` 一页 → **骨架**。

> 结论：A 线是"设计过、写了一部分、从未端到端跑通"的半成品。

## 三、能不能整合

### 3.1 总体判断：**部分整合**

| 对象 | 处置 | 理由 |
|---|---|---|
| B 线 `backend/`（worker/api/dd/sources）+ `ReportEngine/task_store|tasks` + `frontend/` | **保留为唯一主线** | 已跑通、分层清晰、有证据链 |
| B 线旧接口 `/api/report` + Redis Stream | **保留但标 deprecated** | 旧页面仍在用，不能立即删；P1 切 React 后下线 |
| A 线 `server/` 的**鉴权与用户概念** | **合并**进 `core` schema | 多用户是终局需求，但应长在 B 线的模型上 |
| A 线 `server/` 的**代码与进程** | **废弃** | 它是基座单任务时代的代理层，前提已失效 |
| A 线 `web/`（Vue） | **废弃** | 断链（缺 3 页 + 端口错），修复成本高于重写 |
| A 线 `wxapp/` | **废弃/归档** | 1/7 页，纯骨架 |
| `templates/index.html` + Streamlit | **降级为调试入口**，P1 后从 `/` 移除 | 仍有运维价值（看引擎原始输出） |

### 3.2 整合路径与顺序

```text
第 1 步（0.5 人日）  冻结 A 线：server/ web/ wxapp/ 移入 legacy/，README 标注 deprecated
第 2 步（0.5 人日）  修交付：.gitignore 放行 config.example.py、补 rq、提交悬空 15 文件
第 3 步（3–5 人日）  统一状态：core.task_step 为唯一事实源，Redis Stream 仅作通知
第 4 步（3 人日）    统一入口：Flask "/" 切到 React 构建产物，旧页移到 /legacy
第 5 步（3–4 人日）  鉴权上移：users 概念并入 core.app_user，/api/v1 接 JWT
第 6 步（随 P1）     统一产物：final_reports/ 仅作导出，索引走 core.artifact
```

**预计总工作量：10–13 人日**（不含 P1 业务开发）。估算依据：第 3 步涉及 2 处 SSE + 2 处状态读写；第 4 步涉及首页路由与构建挂载；第 5 步涉及 9 张表加字段与中间件。

### 3.3 风险点

| 风险 | 影响 | 缓解 |
|---|---|---|
| 删 `server/` 丢鉴权设计 | 多用户需求来时重做 | 先把 `models.py` 的用户/角色字段抄进 `core` schema 草案，再删代码 |
| 上线切换到 React 后旧 Streamlit 页面不可达 | 运维失去原始视图 | 保留 `/legacy` 路由一个版本周期 |
| 统一状态源时 Redis 与 PG 双写不一致 | 任务状态错乱 | 先读 PG 为准、Redis 只发事件；加对账脚本 |
| 已改造基座无法跟随上游 BettaFish 升级 | 长期维护成本 | 在 README 记录改动点清单（`flask_interface` / `agent` / `runner`） |

### 3.4 直接回答："两条线的产物能不能拼成一套完整可跑的系统？"

**不能原样拼装** ✅。原因不是代码质量，而是**运行时契约互相矛盾**：

1. **端口**：两个 Vite 都默认 5173，同时起必冲突（`frontend/vite.config.ts:8`、`web/vite.config.ts` 未指定端口）。
2. **进程**：A 需要 5000（基座）+ 8000（FastAPI）；B 只需要 5000 + RQ worker。同时跑等于两套后端都连同一个基座，且都假设自己掌握任务状态。
3. **数据库**：A 用 `analysis_tasks`/`reports`；B 用 `core.task`/`core.artifact`。同一份报告会有两条索引，无法判断哪条为准。
4. **目录竞争**：A 的 `Report` 存 `final_reports/` 路径；B 的 `core.artifact` 也指向产物。两边都能写，清理策略不同（A 按文件删，B 按记录删）。
5. **任务语义**：A 的 `pipeline.py:51-52` 明确假设"基座同一时刻只允许一个报告任务"；B 已用 RQ 双队列打破该假设。A 的重试逻辑在 B 环境下会变成无意义轮询。

**结论**：A 线必须"拆概念、弃进程"；把 `server/` 当可运行组件保留，是这次冲突里最贵的误判。

## 五、往后的规矩

### 5.1 分支与提交

| 规则 | 具体做法 |
|---|---|
| `main` 保护 | 禁止直推；至少一次自查清单通过后再合并 |
| 分支命名 | `feat/<line>-<topic>`、`fix/<topic>`、`chore/<topic>`；`line` 取 `dd`/`pr`/`infra`/`ui` |
| 必须开分支的情况 | 改动 > 3 个文件、跨模块、涉及 schema/接口、涉及删除目录 |
| 合并方式 | squash 合并，保持 main 线性；提交信息必须含"模块 + 动机" |
| 目录所有权 | 一个分支只改一个顶层目录（`backend/`、`ReportEngine/`、`frontend/` 二选一），跨目录需在 PR 说明里列出 |

### 5.2 提交前检查清单（打印出来贴墙上）

```text
[ ] 干净克隆能跑：git clone 到临时目录 → 按 README 装依赖 → 关键模块 import 成功
[ ] 依赖已声明：新增 import 的第三方包写进 requirements.txt（不是只写脚本）
[ ] 配置可复现：新增配置项同时更新 config.example.py 与 .env.example
[ ] 密钥未入库：git diff 里无 sk-*/token/password 明文
[ ] 测试通过：python -m unittest discover（基座）+ pytest（server/，若保留）
[ ] 文档基线更新：改动的设计文档头部 baseline commit 改成当前 HEAD
[ ] 无悬空遗留：git status 干净，或未提交项在 PR 描述里逐条说明
```

### 5.3 配置与密钥

**推荐方案：example 模板入库 + `.env` 真值 + 代码不读 `config.py` 真值**

- 保留 `config.py` 作为**默认值定义**（不含密钥），另存一份 `config.example.py` 入库；
- `.gitignore` 改为忽略 `config.py` 但**放行** `config.example.py` 与 `backend/worker/config.py`（后者只有常量，无密钥）；
- 真实密钥只走 `.env`（`pydantic-settings` 已支持，见 `config.py:22`）。

**迁移步骤（0.5 人日）**

1. `cp bettafish-main/config.py bettafish-main/config.example.py`，把 KEY 全部清空；
2. `.gitignore` 增加 `!bettafish-main/config.example.py`、`!bettafish-main/backend/worker/config.py`；
3. README 增加"首次启动：复制 example → 填 `.env`"；
4. CI 增加断言：`config.example.py` 存在且不含 `sk-`。

### 5.4 唯一事实来源

**推荐：新增一份 `ARCHITECTURE.md` 作为唯一事实源，其余文档（现有 10 份，含本复盘）降级为"参考资料"并加状态头。**

| 文档 | 新定位 | 处置 |
|---|---|---|
| `ARCHITECTURE.md`（新建） | **唯一事实源**：当前入口、进程、端口、表结构、目录归属 | 新增，200 行以内，改代码必须同步 |
| `定制化设计方案.md` | 产品愿景（多用户终局） | 保留，头部标 `status: vision` |
| `前端与产品形态升级设计.md` v1.1 | P0/P1 执行设计 | 保留，标 `status: active`，baseline 改为 `7e0c36e` |
| `功能与架构分析.md`、`资源需求评估.md` | 历史分析（基线 `3e035f7`） | 标 `status: archived`，或按当前 HEAD 重写后再启用 |
| `改造模块清单.md` | 排期参考 | 保留，标 `status: plan` |
| `多Agent协作Prompt工程方案.md` | 未来方案 | 保留，标 `status: future` |
| `P0-Ubuntu服务器部署与实施规划.md` | 部署手册 | 保留，标 `status: active` |
| `引擎配置影响分析…`、`Git历史审计.md` | 专项分析/事实记录 | 保留，标 `status: reference` |

规则：**任何文档头必须有三行**——`status`（vision/active/plan/future/archived/reference）、`baseline`（对应 commit）、`owner`（负责人或会话）。没有这三行的文档不得作为执行依据。

### 5.5 并行工作的隔离

| 场景 | 规则 |
|---|---|
| 多会话同时改 | 每个会话一个 `git worktree`（`git worktree add ../wt-<topic>`），禁止共用同一工作区 |
| 改同一模块 | 先在建分支时声明 ownership；第二个会话必须 rebase 后重新申请 |
| 长任务（> 1 天） | 每半天提交一次 WIP（`wip:` 前缀），禁止让改动跨天悬空 |
| 会话交接 | 交接前必须 `git status` 干净或写明未提交项；交接说明写进 `.trae/documents/SESSION_HANDOFF.md` |
| 文档冲突 | 只有 `ARCHITECTURE.md` 有裁决权，其余文档与它冲突时以它为准并更新 |

### 5.6 门禁：最小可行 CI

不引入 GitHub Actions 也可以，先做一个本地脚本 `scripts/ci_smoke.sh`（0.5 人日）：

```bash
#!/usr/bin/env bash
set -euo pipefail
# 1) 配置模板必须存在
test -f bettafish-main/config.example.py
# 2) 禁止明文密钥
! grep -rE "sk-[A-Za-z0-9]{16,}" --include="*.py" . | grep -v example
# 3) 依赖声明一致性：代码里 import 的 rq/redis 必须在 requirements 里
grep -q "^rq" bettafish-main/requirements.txt
grep -q "^redis" bettafish-main/requirements.txt
# 4) 语法编译（不启动服务）
python -m compileall -q bettafish-main/backend bettafish-main/ReportEngine
# 5) 关键模块可导入（用 example 配置 + 假环境变量）
cd bettafish-main && CONFIG_FILE=config.example.py python -c "import backend.worker.enqueue, backend.api.v1"
# 6) 单测
python -m unittest discover -s tests -q
echo "CI smoke OK"
```

后续可把它接进 pre-push hook（`.git/hooks/pre-push`），成本几乎为零，却能挡住本次 3 类问题中的 2 类。
