# BettaFish（微舆）资源需求评估

> 版本基线：本地仓库 `bettafish-main`（main 分支，提交 `3e035f7`）
> 分析方式：**静态代码分析 + 云机实测数据**；未启动服务、未修改代码
> 分析日期：2026-11-08
> 定位：本文是 [功能与架构分析.md](./功能与架构分析.md) 的附录，面向"换本地服务器 / 定配置 / 调参数 / 做迁移"的决策

---

## 0. 结论先行

**当前这套单机架构，推荐配置：8 vCPU / 16GB 内存 / 200GB SSD / 4GB swap。**
- 64G 内存的本地服务器**远超需求**——瓶颈是 LLM API 等待，不是 CPU/内存。给 16GB 就能稳定串行跑完整链路并留出余量；给 32GB 可以三引擎并发 + 情感模型常驻。
- **必须配 swap**（不配的话，4GB 机器已经实测被拖死，见 §7）。
- 磁盘 1T 完全够用，但要注意日志与报告不清理时的长期增长（约 2–8GB/月，见 §4）。

## 1. 各组件资源画像

> 标注规则：**实测** = 本次云机（4GB）真实观测；**估算** = 依赖体积/官方文档推算；**代码推算** = 由配置与流程推算。

| 组件 | 常驻内存 | 磁盘占用 | 依据 | 备注 |
|---|---|---|---|---|
| **Flask 主应用（8080）** | **约 249MB**（实测） | 代码 < 5MB | 实测 `ps` RSS | 含 Socket.IO/eventlet；报告生成时会额外涨到 400–600MB |
| **ReportEngine**（主应用内线程） | **+150~300MB**（估算） | 模板/渲染器约 1MB；产物见 §4 | 代码推算 | 与主应用同进程；出 PDF 时 WeasyPrint 再临时 +150~300MB |
| **QueryEngine Streamlit（8503）** | **约 150–250MB**（实测区间内） | 产物 md+state 约 0.3–0.5MB/次 | 实测 + 样本体积 | 纯联网 + LLM，无本地模型 |
| **MediaEngine Streamlit（8502）** | **约 200–300MB**（实测区间内） | 产物约 0.12–0.15MB/次 | 实测 + 样本体积 | 多模态搜索返回卡片，图片不入库 |
| **InsightEngine Streamlit（8501）** | **约 400–500MB**（实测峰值 456MB） | 产物约 0.05–0.7MB/次 | 实测 | **`torch`/`transformers` 在模块导入期就被加载**（`InsightEngine/agent.py:14`、`InsightEngine/tools/sentiment_analyzer.py`），这是它比其他引擎重一倍的根因 |
| **ForumEngine**（主应用内线程） | **< 50MB**（估算） | `logs/forum.log` 增长 | 代码推算 | 只读日志 + 低频率 LLM 调用 |
| **MindSpider（爬虫）** | **按需进程**，不常驻 | 见 §4 | 代码推算 | 主应用只在启动时 `initialize_database()`；爬取靠手动命令行 |
| **PostgreSQL 15** | **约 80–150MB**（估算） | 安装约 200MB；数据见 §4 | 官方典型值 | 26 张表；`shared_buffers` 默认 128MB |
| **pgvector** | 不常驻 | 扩展约 5–10MB | 代码检索 + `deploy/init_db.sql` | **当前代码未使用**，可装可不装（见 §5） |
| **Redis** | 不常驻 | — | 代码检索 | **当前主流程不依赖，可不装** |
| **Playwright / Chromium** | **每个浏览器实例约 250–400MB**（估算）；实测 2 个实例叠加是压垮 4GB 机器的关键 | **534MB**（实测） | 实测磁盘 + 官方典型值 | 仅 MindSpider 爬虫需要；跑报告时不需要 |
| **情感分析模型（若开启）** | **约 700MB–1GB**（估算，含 torch 运行开销） | **约 700MB**（首次从 HuggingFace 下载） | 代码推算 | 仓库内 `SentimentAnalysisModel/` 只有 178MB 训练产物，**没有推理权重**，首次运行必然联网下载 `tabularisai/multilingual-sentiment-analysis` |
| **聚类模型（SentenceTransformer）** | **约 300MB**（估算） | **约 470MB**（首次下载 `paraphrase-multilingual-MiniLM-L12-v2`） | 代码推算 | `ENABLE_CLUSTERING=True`（`InsightEngine/agent.py:32-36`），检索结果 > 50 条时触发 |
| **Python venv（全量依赖）** | — | **约 1.8–2.5GB**（估算） | requirements 重量级包推算 | torch(CPU) ~900MB、opencv ~90MB、pandas/numpy ~100MB、transformers/sentence-transformers ~120MB、weasyprint/playwright 等 |
| **项目代码本体** | — | **约 200MB**（实测，含 `SentimentAnalysisModel` 178MB） | 实测目录体积 | 源码本身很小，体积主要来自模型训练产物 |

**一句话**：常驻大头是"三个 Streamlit（其中 Insight 因 torch 最重）+ PostgreSQL + Flask"；**峰值大头是"Chromium 爬虫 + 情感/聚类模型"**，这两项也是最容易被误开、且默认就开着的东西。

## 2. 三档配置建议

### 档位 A：最低可运行（只做安装校验 / 开首页 / 跑单测）

| 项 | 建议 |
|---|---|
| CPU | 2 vCPU |
| 内存 | **2GB**（4GB 更稳） |
| 磁盘 | 20GB |
| swap | 可选 2GB |
| 预计峰值内存 | **约 0.8–1.2GB**（Flask 250MB + 单个轻量引擎 200–300MB + 系统基础） |
| 实际能力边界 | ✅ 能开首页、`/api/status`、读写配置、`pytest tests`（实测 36 passed）<br>❌ **不能跑完整链路**（Insight 单进程就要 400–500MB，再叠加报告生成必然吃紧）<br>❌ 不能同时起三个引擎 |
| 适用场景 | 功能演示、CI 冒烟、开发调试前端 |

### 档位 B：单用户串行完整链路（推荐的最小生产配置）

| 项 | 建议 |
|---|---|
| CPU | **4 vCPU** |
| 内存 | **8GB**（最低 6GB） |
| 磁盘 | **100GB SSD** |
| swap | **必须 4GB** |
| 预计峰值内存 | **约 2.0–3.0GB**（Flask 250 + 单引擎 500 + 报告生成 500 + PG 150 + 系统/缓存） |
| 实际能力边界 | ✅ 能跑通完整报告（**前提是按 §3.2 调参**，否则 Insight 会拖到 1 小时以上）<br>✅ 可以一个引擎跑完停掉、再起下一个（串行）<br>⚠️ 不能三引擎同时驻留 + 同时出报告 + 同时爬取 |
| 适用场景 | 单用户日常出报告 |

### 档位 C：并发运行（三引擎同时驻留 + 报告 + 爬虫）

| 项 | 建议 |
|---|---|
| CPU | **8 vCPU**（LLM 等待为主，CPU 不是瓶颈，但多进程调度需要余量） |
| 内存 | **16GB**（最低 12GB） |
| 磁盘 | **200GB SSD** |
| swap | 4GB（建议保留，作为 OOM 缓冲） |
| 预计峰值内存 | **约 4.0–6.0GB**：Flask 250 + 三引擎 1.2GB + 报告 500 + PG 200 + Chromium 400 + 系统缓存；若加载情感模型再 +1GB |
| 实际能力边界 | ✅ 三引擎同时跑 + 报告生成 + 爬虫任务并行<br>✅ 可支撑 2–3 个并发用户（但**报告任务仍是单例串行**，见架构文档 §2.6 技术债 #6） |
| 适用场景 | 小团队共用 |

**关于你新的本机（64G / 1T）**：
- 直接给这套系统 **16GB / 8 vCPU / 200GB** 的虚拟机或容器配额就足够，剩余资源留给其他服务。
- 如果打算"边跑舆情边跑本地大模型"，再做隔离；否则 64G 对当前架构是**明显过剩**——因为耗时 90% 以上花在等待第三方 LLM 返回，加内存不会让报告更快（详见 §3.1）。

## 3. 性能瓶颈判定

### 3.1 InsightEngine 为什么"20 分钟只到 2/5 段"

**结论：约 90–95% 的时间是 LLM API 等待，不是本地 CPU 计算。加硬件解决不了。**

耗时构成（按代码推算，与实测 20 分钟/2 段吻合）：

| 环节 | 单段消耗 | 代码位置 | 判定 |
|---|---|---|---|
| 关键词优化（每主题 1 次 LLM） | 10–30s | `InsightEngine/agent.py` 关键词优化流程（`KEYWORD_OPTIMIZER_*`） | LLM 等待 |
| 本地库检索（每段 1 次，跨 7 张平台表 + 7 张评论表） | 1–5s | `InsightEngine/tools/search.py:193-330` | 本地 SQL，快 |
| 段落初始总结（1 次 LLM，prompt 可达 **500KB**） | **60–120s** | `InsightEngine/agent.py:512` 起的段落循环；`MAX_CONTENT_LENGTH=500000` | **LLM 等待（超长输入是主因）** |
| 反思循环（默认 2 次/段，每次 2 次 LLM + 1 次检索） | 2 × 90–180s | `SingleEngineApp/insight_engine_streamlit_app.py:63`（`max_reflections=2`） | **LLM 等待（占比最高）** |
| 首次检索的情感模型初始化（联网下载 HF，内网会超时） | 一次性 30–300s（失败后自动降级） | `InsightEngine/tools/sentiment_analyzer.py:32` + `agent.py` 搜索后处理 | 网络等待（可消除） |
| 检索结果 >50 条触发的聚类（联网下载 SentenceTransformer） | 一次性 30–300s | `InsightEngine/agent.py:32-36` | 网络等待（可消除） |
| 任一 LLM 偶发 429/5xx 触发的重试 | **每次 +60~600s** | `utils/retry_helper.py:228-233`（6 次、首等 60s、指数退避、单次上限 600s） | **等待放大器（最隐蔽）** |

**必须点名的两个"隐形杀手"**：
1. **`MAX_CONTENT_LENGTH=500000`**（`InsightEngine/utils/config.py:28`，streamlit 应用同样覆盖为 500000，`insight_engine_streamlit_app.py:64`）：每段 prompt 可能塞进几十万字符，单次 LLM 调用自然慢一个数量级。
2. **`LLM_RETRY_CONFIG`**（`utils/retry_helper.py:228-233`）：最坏情况下**单次调用可等 35 分钟**（60+120+240+480+600+600）。只要遇到一次限流，用户就会看到"卡住不动"。

**哪些瓶颈加硬件能解决**：
- ✅ 三引擎/多任务的**内存不足**（加内存）
- ✅ 并发时的 CPU 争抢（加核）
- ✅ 本地 PDF 渲染、HTML 生成的瞬时 CPU（加核，收益小）

**哪些只能改参数/改设计**：
- ❌ LLM 首 token/总时长（改参数：缩短 prompt、减少反思、收缩超时与重试）
- ❌ 反思循环次数（改参数）
- ❌ 联网下载模型（改配置：关闭或预下载）
- ❌ Streamlit 会话模型导致的"关页面即中断"（改设计）

### 3.2 可调参数清单（配置项 + 位置 + 当前值 + 建议值）

| # | 配置项 | 文件:行号 | 当前值 | 建议值 | 预期收益 |
|---|---|---|---|---|---|
| 1 | `MAX_REFLECTIONS` | `InsightEngine/utils/config.py:25`；实际生效值被 `SingleEngineApp/insight_engine_streamlit_app.py:63` 覆盖 | 3 / 实际 **2** | **0–1** | 单段 LLM 调用减少 33–50%，整体快 30–45% |
| 2 | `MAX_PARAGRAPHS` | `InsightEngine/utils/config.py:26` | 6 | **3–4** | 段落数减少 33–50% |
| 3 | `MAX_CONTENT_LENGTH` | `InsightEngine/utils/config.py:28`；`insight_engine_streamlit_app.py:64` | 500000 | **20000–50000** | 单次 LLM 延迟下降一个量级 |
| 4 | `SEARCH_TIMEOUT` | `InsightEngine/utils/config.py:27` | 240s | **60s** | 检索异常快速失败 |
| 5 | `ENABLE_CLUSTERING` | `InsightEngine/agent.py:32-36` | **True** | **False** | 去掉 HF 模型下载与约 300MB 内存 |
| 6 | `SENTIMENT_ANALYSIS_ENABLED` | `InsightEngine/tools/sentiment_analyzer.py:32` | **True**（硬编码，无环境变量） | **False**（需代码改一行，或预下载模型） | 去掉 700MB 下载与首次检索卡顿 |
| 7 | `LLM_RETRY_CONFIG` | `utils/retry_helper.py:228-233` | 6 次 / 首等 60s / ×2 / 上限 600s | **2 次 / 5s / ×2 / 60s** | 最坏等待 35min → 约 2min |
| 8 | `SEARCH_API_RETRY_CONFIG` | `utils/retry_helper.py:235-240` | 5 次 / 2s / ×1.6 / 25s | **2 次 / 2s / ×1.6 / 10s** | 检索异常快速失败 |
| 9 | `LLM_REQUEST_TIMEOUT`（默认值） | `InsightEngine/llms/base.py:43-47` | **1800s** | **300s** | 单次卡死快速失败（环境变量可覆盖） |
| 10 | `LLM_REQUEST_TIMEOUT`（报告） | `ReportEngine/llms/base.py:54-58` | **3000s** | **600s** | 同上 |
| 11 | `MAX_RETRIES` / `API_TIMEOUT` / `MAX_RETRY_DELAY` | `ReportEngine/utils/config.py:60-62` | 8 / 900s / 180s | **3 / 300s / 60s** | 报告失败快速返回 |
| 12 | Query/Media `max_content_length` | `SingleEngineApp/query_engine_streamlit_app.py:64`、`media_engine_streamlit_app.py:65` | 20000 | 保持 | 已合理 |
| 13 | `MAX_CONCURRENCY_NUM` | `MindSpider/DeepSentimentCrawling/MediaCrawler/config/base_config.py:76` | 1 | 保持（服务器上不要调高） | 并发高易触发反爬 |
| 14 | `ENABLE_CDP_MODE` | 同上 `base_config.py:40` | **True** | **False**（服务器无桌面 Chrome，必须用自带 Chromium） | 否则爬虫启动即失败 |
| 15 | `ENABLE_GET_COMMENTS` / `CRAWLER_MAX_NOTES_COUNT` | 同上 `base_config.py:82` 及平台参数 | True / 20 条评论、5 条笔记 | 按需下调 | 降低爬取量与内存 |

> 建议顺序：**先做 5、6、7、9，再做 1、2、3**。前四项是"去掉不可控等待"，后三项是"减少工作量"。

### 3.3 Query / Media 为什么各约 5 分钟

| 环节 | 占比（估算） | 说明 |
|---|---|---|
| LLM 调用 | **约 70%** | 5 段 × （1 次初始总结 + 2 次反思 × 2 次 LLM）≈ 15 次调用，单次 15–30s |
| 搜索 API 往返 | **约 25%** | Tavily（Query）/ Anspire 或 Bocha（Media），单次 3–8s；`SEARCH_TIMEOUT` 默认 240s 偏大 |
| 本地组装/渲染 | **约 5%** | 纯字符串拼接，可忽略；Media 不做图片下载/PDF 渲染 |

**结论**：Query/Media 的 5 分钟是**正常的 API 等待**，不是性能问题；想更快只能减少反思次数或换更快的模型。

## 4. 磁盘增长预估

### 4.1 单次分析产物（实测样本 + 推算）

| 产物 | 实际体积 | 依据 |
|---|---|---|
| Query 报告 md | 4.5–16.2KB | 实测样本 |
| Query 状态 json | 250–483KB | 实测样本 |
| Media 报告 md | 4.5–11.5KB | 实测样本 |
| Media 状态 json | 111–117KB | 实测样本 |
| Insight 报告 md | 4.1–4.8KB | 实测样本 |
| Insight 状态 json | 50–662KB | 实测样本 |
| 最终 HTML | 89.9KB | 实测样本 |
| 整本 IR json | 1–3MB（估算） | 章节结构展开 |
| 章节 JSON | 约 0.5–2MB（估算） | 每章一份 |
| 日志（一次分析期间） | 1–5MB（实测日志增长） | `logs/*.log` |
| PDF（按需） | 1–3MB（估算） | WeasyPrint 输出 |

**单次完整分析合计：约 3–8MB**（含 PDF 约 5–11MB）。

### 4.2 长期增长速率

| 场景 | 报告侧 | 爬虫侧（若每日爬取） | 合计 |
|---|---|---|---|
| 每天 5 次分析 | 15–40MB/天（≈0.5–1.2GB/月） | 25–100MB/天（≈0.8–3GB/月） | **约 1.5–4GB/月** |
| 每天 20 次分析 | 60–160MB/天（≈2–5GB/月） | 100–400MB/天（≈3–12GB/月） | **约 5–17GB/月** |

**附加增长项**：
- Streamlit 缓存：数十 MB，重启即清；
- 若开启 debug 日志：`logs/` 可涨到 100MB+/天；
- HuggingFace 模型缓存（若预下载）：+0.7–1.2GB（一次性）；
- venv：1.8–2.5GB（一次性）。

**建议**：200GB 数据盘 + `logrotate`（日志按天切、保留 14 天）+ 报告保留 90 天，足以支撑一年以上。

### 5.2 容易踩坑的"隐性网络依赖"

- **情感分析**：`InsightEngine/tools/sentiment_analyzer.py:32` 硬编码 `SENTIMENT_ANALYSIS_ENABLED = True`，首次检索即尝试从 HF 下载约 700MB 模型；内网环境下会超时（异常被捕获、自动降级，但会拖慢首次搜索）。
- **聚类**：`InsightEngine/agent.py:32-36` `ENABLE_CLUSTERING=True`，检索结果 >50 条时加载 `paraphrase-multilingual-MiniLM-L12-v2`（约 470MB）。
- **报告 HTML 的 jsPDF**：`ReportEngine/renderers/html_renderer.py:433` 引用了 cdnjs 的 jsPDF，离线打开报告时"浏览器端导出 PDF"按钮失效；**服务端 WeasyPrint 导出不受影响**。

### 5.3 运行期**不需要**访问

| 项 | 说明 |

| GitHub | 仅拉代码/更新时需要 |
| npm / 前端 CDN | 前端是本地单文件，无构建 |
| HuggingFace | **只要关闭情感分析与聚类、或预下载模型后**，运行期完全不需要 |

| 用途 | 推荐替代 |

## 6. 迁移到本地服务器的注意事项

### 6.1 Python 依赖能否离线迁移

| 方案 | 做法 | 可靠性 | 建议 |
|---|---|---|---|
| **整目录搬运 venv** | 同发行版、同 Python 小版本、同架构时，`tar` 整个 `.venv` 过去 | 中（路径/权限易出问题） | 仅应急 |
| **离线 wheel 包**（推荐） | 在联网机 `pip download -r requirements.txt -d wheels/ --only-binary=:all:`，目标机 `pip install --no-index --find-links=wheels -r requirements.txt` | 高 | ✅ 首选 |
| 目标机直连内网 PyPI 镜像 | 配 `pip.conf` | 高 | 若有内网源 |

**必须注意的版本钉死**：`requirements.txt` 固定了 `streamlit==1.28.1`、`flask==2.3.3`、`eventlet==0.33.3`。README 建议 **Python 3.11**；云机验证时用 3.12 需要 `virtualenv + PYTHONPATH` 绕行。**建议本地服务器统一用 3.11**，避免兼容性踩坑。

### 6.3 数据库如何迁移

### 6.4 `.env` 与配置文件差异点

- 根 `config.py` **被 `.gitignore` 忽略**（`.gitignore:291`、`298`），新机器上要么从旧机拷贝，要么只靠 `.env`（`config.py:111` 指定 env_file）。
- 迁移时必须改的键：`HOST`、`PORT`、`DB_HOST/PORT/USER/PASSWORD/NAME/DIALECT`、各家 `*_ENGINE_API_KEY/BASE_URL/MODEL_NAME`、`KEYWORD_OPTIMIZER_*`、`TAVILY_API_KEY`、`SEARCH_TOOL_TYPE`、`ANSPIRE_API_KEY`/`BOCHA_WEB_SEARCH_API_KEY`。
- 建议：新机器上用 `.env` 作为唯一真源，**不要把密钥写进 `config.py`**（现有 `/api/config` 会明文回传，见架构文档技术债 #2）。

### 6.5 路径硬编码排查结果

- **运行时代码中没有 `/opt/gitdownload` 之类的绝对路径**（全仓库检索无命中）。
- 唯一发现的硬编码出现在**辅助脚本**：`ReportEngine/scripts/export_pdf.py` 里有作者本机路径（非运行期路径），不影响部署。
- 相对路径依赖：所有产物目录都是相对当前工作目录（`query_engine_streamlit_reports/` 等），因此**必须从项目根目录启动**，否则产物会散落。

### 6.6 Playwright 浏览器处理

| 项 | 做法 |
|---|---|
| 浏览器目录 | 通过 `PLAYWRIGHT_BROWSERS_PATH` 指定（云机验证时用的是独立目录，约 534MB） |
| 离线安装 | 联网机 `playwright install chromium` 后打包 `~/.cache/ms-playwright`；或指定 `PLAYWRIGHT_BROWSERS_PATH` 后整体复制 |
| 必须改的配置 | **`ENABLE_CDP_MODE` 由 `True` 改为 `False`**（`MediaCrawler/config/base_config.py:40`），否则会去找本地桌面 Chrome 的 CDP 端口而不是自带的 Chromium |
| 无头模式 | `HEADLESS=True` 已默认（`base_config.py:31`） |
| 权限 | 容器/低权限用户运行时需要 `--no-sandbox`（Chromium 在 root 下必须） |

## 7. 附：本次云机（4GB）故障实测复盘（作为容量依据）

| 观测 | 数值 |
|---|---|
| 机器内存 | 4GB，**无 swap** |
| 启动前可用内存 | 约 443MB |
| 常驻：Flask 8080 | 约 249MB |
| 常驻：三个 Streamlit | 112–456MB/个 |
| 额外：Playwright 浏览器 | 2 个实例（因脚本重复执行产生） |
| 额外：直连 InsightEngine 脚本 | 1 个进程（含 torch） |
| 结果 | 8080 端口 TCP 可连但 **HTTP 120s 无响应**；SSH 密码通过但**会话建立即被断开**（`MaxStartups` 一度占满）；公网 ping 0% 丢包 |

**结论**：
1. **4GB + 无 swap 跑"三引擎 + 报告 + 浏览器"是危险线**，一旦叠加就进入"谁都不能工作"的状态（不是单个进程被 OOM kill，而是整体卡死）。
2. 迁移到本地服务器时：**8GB 起步、16GB 舒适、必须配 swap**；并且**不要同时启动 Chromium 与 InsightEngine**（两者叠加约 1GB）。
3. 长任务的**重试等待**（`LLM_RETRY_CONFIG`）会让"看起来卡死"变成常态，建议按 §3.2 收紧。

## 8. 最终建议（一页版）

| 决策项 | 建议 |
|---|---|
| 本地服务器配额 | **8 vCPU / 16GB / 200GB SSD / 4GB swap**（64G 机器上开一台这样的 VM 即可） |
| Python | **3.11**（不要用 3.12） |
| 依赖迁移 | 离线 wheel 包（`pip download`），不要直接搬 venv |
| 数据库 | PostgreSQL 15 + 专用角色；pgvector 可跳过；Redis 不装 |
| 必改配置 | 关闭情感分析、关闭聚类、Insight 反思 2→1、内容长度 500000→20000、收紧 LLM 重试与超时；`ENABLE_CDP_MODE=False` |
| 运维 | systemd 守护 8080；日志 logrotate；报告 90 天保留；**先加鉴权再开放 8080** |
