## 0. 核心结论

### 判断一：这不是"加两个入口"，是两个操作节奏完全不同的工作台

背调是**案卷制**——一个对象、一份卷宗、几天到几周、多轮补充、要求可追溯；
舆情是**值班制**——一条告警、几分钟响应、漏报即事故、要求时效。

两者的页面主干不同：背调的主干是「**对象档案**」，舆情的主干是「**待处置队列**」。如果把两者塞进同一套页面，背调会被任务列表淹没，舆情会被案卷详情拖慢。

**结论：共享内核（Object / Task / Evidence / Artifact），分叉外壳（两个工作台）。**

### 判断二：前端升级的前提是后端「去会话化」，否则只是换皮

现状三个引擎的进度是 **Streamlit 自己渲染的**，关掉浏览器页面，任务就断（方案 A §1.3 已记录）。而 `ReportEngine` 用模块级全局变量 + 单锁管理任务：

```python
# ReportEngine/flask_interface.py:31-32
current_task = None
task_lock = threading.Lock()
```

**这意味着整个系统同一时刻只能跑一个报告任务**，多用户根本无从谈起。

**结论：P0 必须先做异步任务队列 + 结构化进度事件，前端才有东西可订阅。** 先做前端是本末倒置。

### 判断三：Evidence 必须是一等公民，报告可回溯是产品的技术底座

背调报告一旦有一句编造的数字，产品就废了。所以不是"报告里附个来源列表"，而是：

- 每一句事实结论 → 绑定 `evidence_id`
- 每一条 evidence → 绑定 `source_url` + `quote` + 抓取时间 + 置信度
- 渲染时角标可点击 → 右侧抽屉直接看原文

**这条链路要在数据模型层固化，不能靠 prompt 约定。**

### 三个判断的代价

| 判断 | 不做会怎样 |
|---|---|
| 双工作台 | 上线后业务方会要求"把任务列表挪走""把告警置顶"，反复改，最后回到两个系统 |
| 先去会话化 | 前端做得再好，用户关页面任务就丢，投诉必然发生 |
| Evidence 一等公民 | 报告被质疑一次就失去信任，且无法事后补救（历史报告无证据链） |

### 0.1 决策更新（v1.1，2026-11-08）

用户三项业务决策已明确，对本文档的影响：

| # | 决策 | 设计影响 |
|---|---|---|
| ① | **仅内部使用，不对客户部署，只对客户出报告** | 系统边界收窄为内部工具：P3 的多租户强化、SSO、对外 REST API、移动端适配全部砍掉；RBAC 从三层（dept/team/project）简化为「部门 + 角色」两层。**反向强化一件事**：报告（PDF + 证据附录）成为唯一对客户的交付物，其专业度与合规表述（§5.1.3、§5.2.1④）从"重要"升级为"客户直接看到的门面" |
| ② | **数据预算未定，先用免费额度做 demo** | P0/P1 数据源限定免费额度（清单见 §6.1）：AkShare、巨潮、天眼查免费额度、Tavily 免费额度。**评分卡三态（§5.1.2）从优化项变成必需品**——免费源覆盖不全，「数据缺失」会高频出现，demo 必须把"查不到"和"确有风险"区分开，否则免费 demo 的报告会制造大量假风险。付费源留接口不接，预算到位后热插 |
| ③ | **预警暂不做，后续定位 2 小时级别** | 舆情线在 P0–P2 降级为**人工发起的咨询任务**（部门提需求 → 分析师发起归因分析 → 出报告），不做系统主动扫描、告警、值班台。预警整体后移到 P3。2h 级别意味着 **APScheduler 定时轮询即可，不需要流式/消息队列架构**——此选型现在定死，避免将来返工。响应时限表相应修订（§5.2.2） |

**三个核心判断不变**：双工作台仍是终局形态，只是舆情工作台的「值班台 + 告警队列」推迟到 P3；P0–P2 的舆情侧只有「人工发起归因分析」一个入口。分期总量从 155 人日调整为 141 人日（§6.5）。

## 1. 两条产品线的本质差异

### 1.1 差异全景

| 维度 | 背调线 | 舆情线 |
|---|---|---|
| **工作模式** | 案卷制，一人主责 | 值班制，轮班 |
| **时间尺度** | 3 天 – 3 周 | 15 分钟 – 3 天 |
| **触发方式** | 人工立项 | 系统告警 + 人工关注 |
| **核心实体** | Object（公司/人） | Event（事件）+ Alert |
| **页面主干** | 对象档案页 | 待处置队列 |
| **数据特征** | 宽而深（多源、多维度、历史全量） | 窄而快（近期、增量、实时） |
| **失败代价** | 结论错误 → 投资/合作决策错误 | 漏报 → 公关危机扩大 |
| **成功指标** | 报告被采纳率、证据覆盖率 | 首响时长、漏报率、误报率 |
| **典型操作** | 发起任务 → 等 → 复核 → 编辑 → 导出 | 收告警 → 判定 → 处置 → 归档 |
| **协作方式** | 串行（分析员 → 复核人 → 决策人） | 并行（值班 + 主管 + 业务方同时看） |
| **留存要求** | 长期（案卷要能回溯 3 年） | 中期（事件闭环后归档） |

### 1.2 为什么不能"在现有页面上加两个入口"

现有 `templates/index.html` 的心智模型是**一次性主题分析**：

```
输入 query → 三个 iframe 并行跑 → 等 20 分钟 → 出一份 md
```

它的信息架构里**没有"对象"这个概念**——query 是自由文本，产物是文件，没有主键，无法二次查看、无法增量补充、无法关联到别的任务。

三条硬冲突：

| 冲突 | 具体表现 |
|---|---|
| **主键冲突** | 现有一切以「query 字符串」为标识；背调必须是以 `object_id` 为标识的长期档案，同一公司第 2 次背调要能看到第 1 次的结论 |
| **节奏冲突** | 背调页面的默认视图是"这一卷宗现在到第几章"；舆情页面的默认视图是"过去 1 小时有几条 P0"。同一个首页无法同时满足 |
| **权限冲突** | 背调按项目隔离（A 项目看不到 B 项目）；舆情按部门共享（全员可见告警）。同一套列表页无法同时套两种过滤规则 |

> 佐证：现有前端连"历史报告列表"都没有——`/api/report/history` 这个路由在 `ReportEngine/flask_interface.py` 的 14 个路由中**并不存在**，产物只能靠文件名猜。这已经说明它不是为"多任务、可回溯"设计的。

## 2. 统一数据模型

### 2.1 设计原则：不重复造表

方案 A §5.5 已经定义了 `kb.company` / `kb.person` / `kb.event` / `kb.evidence`。
本节**不重新定义业务实体**，而是补三样方案 A 没覆盖的东西：

1. **`core.object`** —— 统一对象注册表（把 company/person/event 抽象成同一种可被任务引用的东西）
2. **`core.task`** —— 任务与任务步骤（方案 A 没有任务概念）
3. **`core.artifact`** —— 产物与**句级引用绑定**（方案 A 只到 evidence，没到"报告里哪一句"）

### 2.2 四类实体关系

```text
                    ┌─────────────┐
                    │ core.object │  object_id（稳定，永不变）
                    │  type:      │
                    │  company /  │
                    │  person /   │
                    │  event      │
                    └──┬───┬───┬──┘
                       │   │   │ ref_id
          ┌────────────┘   │   └────────────┐
          ▼                ▼                ▼
   kb.company       kb.person         kb.event
   （方案A 已定义）  （方案A 已定义）   （方案A 已定义）

   object_id ──┬──< core.task          （一个对象可有多个任务）
               │        │
               │        ├──< core.task_step
               │        │
               │        └──< core.artifact ──< core.artifact_block
               │                                      │
               └──< core.evidence ────────────────────┘
                         ▲                    core.artifact_citation
                         │                     （句 ↔ 证据）
                    task_id（可空：长期资产）
```

**关键设计：`object_id` 是稳定主键，`ref_id` 可改。**
当方案 A §5.2 的实体对齐算法把两条公司记录合并时，只需改 `core.object.ref_id`，**所有历史任务、证据、报告都不会失效**。这是把"实体合并"这个高频操作与"业务数据"解耦的关键。

### 2.3 Evidence 一等公民

#### 2.3.1 `fact` 与 `quote` 的区别（最容易做错的地方）

| 字段 | 含义 | 例子 |
|---|---|---|
| `fact` | **系统归一化后的事实断言**（结构化，可比较、可聚合） | "该公司于 2024-03-12 被上海市市场监管局罚款 200 万元" |
| `quote` | **原文片段**（LLM 不可改写，原样保存） | "……责令当事人停止发布违法广告，罚款人民币贰佰万元整……" |

- `fact` 用于检索、聚合、评分卡计算
- `quote` 用于报告引用、人工复核、争议时自证
- **`fact` 可以由 LLM 从 `quote` 抽取，但必须做后校验**（数字回查，见 §4.4）

#### 2.3.2 置信度不是拍脑袋

`confidence`（0–100）的来源必须可解释，写入 `confidence_reason`：

| 来源类型 | 基准分 | 调整规则 |
|---|---|---|
| 政府/监管直采（gsxt、信用中国、裁判文书原文） | 95 | 有原文 PDF → 100 |
| 上市公司公告（巨潮） | 95 | — |
| 商业 API（天眼查/企查查） | 85 | 与官方源交叉一致 → 95；冲突 → 60 |
| 权威财经媒体 | 70 | 两家以上独立源一致 → 85 |
| 一般媒体/自媒体 | 50 | 仅作线索，不进评分卡 |
| LLM 推断（非抽取） | ≤ 40 | **禁止进入评分卡，只能进"待核实"** |

### 2.4 报告可回溯的三种技术方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 行内角标 + ID 映射 | 正文写 `……罚款 200 万元[E12]`，`E12 → evidence_id` | 实现简单、导出友好、Markdown 兼容 | 只能定位到句，不能定位到"哪几个字" | **必选** |
| B. 文本区间锚点 | 存 `(block_id, start_offset, end_offset)` | 最精确，可高亮 | 一旦编辑正文，偏移全部失效，需要 OT/CRDT | 只在**最终定稿时**生成快照，不用于编辑期 |
| C. 双向绑定表 | `artifact_citation(block_id, sentence_idx, evidence_id)` | 可查询"这条证据被哪些报告引用" | 需要额外维护 | **必选** |

**推荐组合：A + C。**

- 编辑期：正文用 `[E12]` 角标（A），保存时解析成 `artifact_citation` 行（C）
- 定稿时：再生成一次 B 的区间快照，供 PDF 高亮与"原文定位"使用
- 这样既不牺牲编辑体验，又能在定稿后做到像素级定位

**为什么不用 B 做主方案**：报告是要人工编辑的（§4.4），编辑必然导致偏移漂移，维护 OT 的成本远超收益。

### 2.5 DDL 建议

```sql
CREATE SCHEMA IF NOT EXISTS core;

-- ============================================================
-- 1. 统一对象注册表（对 kb.company / kb.person / kb.event 的抽象）
-- ============================================================

    merged_into   BIGINT REFERENCES core.object,
    created_at    TIMESTAMPTZ DEFAULT now(),
    updated_at    TIMESTAMPTZ DEFAULT now(),
    UNIQUE (object_type, natural_key)
);

CREATE INDEX idx_obj_type_name ON core.object (object_type, display_name);
CREATE INDEX idx_obj_ref ON core.object (object_type, ref_id);

-- 对象别名（跨类型统一入口，便于搜索框一次查全）
CREATE TABLE core.object_alias (

    alias_norm  TEXT NOT NULL,
    source      TEXT,
    UNIQUE (object_id, alias_norm)
);
CREATE INDEX idx_obj_alias_norm ON core.object_alias (alias_norm);

-- ============================================================
-- 2. 任务（异步执行的基本单位）
-- ============================================================
CREATE TABLE core.task (
    task_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    product_line   TEXT NOT NULL CHECK (product_line IN ('dd','pr')),  -- dd=背调 pr=舆情
    task_type      TEXT NOT NULL,
                   -- dd: investment_dd / person_dd / partner_access
                   -- pr: event_trace / sentiment_watch / emergency_plan
    object_id      BIGINT REFERENCES core.object,
    parent_task_id UUID REFERENCES core.task,   -- 子任务（如背调里的"抓财报"）
    status         TEXT NOT NULL DEFAULT 'queued',
                   -- queued/running/waiting_input/succeeded/failed/canceled
    priority       SMALLINT NOT NULL DEFAULT 5, -- 0 最高
    progress       SMALLINT NOT NULL DEFAULT 0, -- 0-100
    stage          TEXT,                        -- 当前阶段（供前端显示中文）
    input          JSONB NOT NULL DEFAULT '{}', -- 模板参数、数据源开关、时间范围
    result         JSONB,                       -- 结构化结果摘要（评分卡分数等）
    error          JSONB,                       -- {code, message, trace_id}
    project_id     BIGINT,                      -- 所属项目（权限隔离）
    requested_by   BIGINT NOT NULL,
    idempotency_key TEXT UNIQUE,                -- 防重复提交
    worker_id      TEXT,
    heartbeat_at   TIMESTAMPTZ,                 -- 心跳，用于检测僵死任务
    created_at     TIMESTAMPTZ DEFAULT now(),
    started_at     TIMESTAMPTZ,
    finished_at    TIMESTAMPTZ
);

CREATE INDEX idx_task_status ON core.task (status, priority, created_at);
CREATE INDEX idx_task_object ON core.task (object_id, created_at DESC);
CREATE INDEX idx_task_project ON core.task (project_id, created_at DESC);

-- 任务步骤（细粒度进度与耗时归因）
CREATE TABLE core.task_step (
    step_id     BIGSERIAL PRIMARY KEY,
    task_id     UUID NOT NULL REFERENCES core.task ON DELETE CASCADE,
    seq         INTEGER NOT NULL,
    name        TEXT NOT NULL,              -- fetch_cninfo / parse_report / llm_chapter_3
    status      TEXT NOT NULL DEFAULT 'pending',
    started_at  TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    duration_ms INTEGER,
    detail      JSONB,                      -- 输入摘要、token 数、错误
    UNIQUE (task_id, seq)
);

-- ============================================================
-- 3. 证据（一等公民）
-- ============================================================
CREATE TABLE core.evidence (
    evidence_id   BIGSERIAL PRIMARY KEY,
    object_id     BIGINT NOT NULL REFERENCES core.object,
    task_id       UUID REFERENCES core.task ON DELETE SET NULL,   -- 可空=长期资产
    fact          TEXT NOT NULL,                 -- 归一化事实断言
    fact_type     TEXT NOT NULL,                 -- registration/penalty/litigation/finance/
                                                 -- bid/ip/sentiment/exec_change

    source_type   TEXT NOT NULL,                 -- gsxt/creditchina/court/cninfo/tianyancha/news/social
    source_name   TEXT,
    source_url    TEXT NOT NULL,
    doc_id        BIGINT,                        -- 指向 kb.kb_document（方案A §5.5）

    quote         TEXT,                          -- 原文片段，LLM 不可改写

    captured_at   TIMESTAMPTZ NOT NULL DEFAULT now(),  -- 抓取时间（与发布时间严格区分）

    confidence_reason TEXT,
    verified_by   BIGINT,                        -- 人工复核人
    verified_at   TIMESTAMPTZ,
    verify_status TEXT DEFAULT 'auto',           -- auto/confirmed/rejected/needs_review

    created_at    TIMESTAMPTZ DEFAULT now(),

);

CREATE INDEX idx_ev_object ON core.evidence (object_id, fact_type, published_at DESC);
CREATE INDEX idx_ev_task ON core.evidence (task_id);

-- ============================================================

    object_id     BIGINT REFERENCES core.object,
    artifact_type TEXT NOT NULL,      -- report_html/report_pdf/report_md/brief/timeline/playbook_instance
    template_code TEXT,               -- investment_dd_v1 / person_dd_v1 / event_trace_v1
    version       INTEGER NOT NULL DEFAULT 1,
    status        TEXT NOT NULL DEFAULT 'draft',   -- draft/reviewing/final
    storage_path  TEXT,               -- 相对路径
    mime_type     TEXT,
    size_bytes    BIGINT,
    sha256        CHAR(64),
    title         TEXT,
    created_by    BIGINT,
    created_at    TIMESTAMPTZ DEFAULT now(),
```

## 3. 后端能力补齐（前端升级的前提）

### 3.1 任务队列

#### 3.1.1 现状的四个硬伤

| 问题 | 证据 | 后果 |
|---|---|---|
| 报告任务全局单例 | `ReportEngine/flask_interface.py:31-32` `current_task = None` + `task_lock` | **同时只能跑一个报告**，第二个人一点就排队或报错 |
| 引擎执行绑浏览器会话 | 三个 Streamlit 脚本在浏览器会话里跑，关页即断 | 背调 20 分钟的任务不敢关页面 |
| 无重试、无超时、无心跳 | 只有 `threading.Thread` | 任务卡死无人知晓，进程重启全部丢失 |
| 进度是"文本日志" | `ReportEngine` 的 `stream/<task_id>` 推的是日志文本 | 前端无法做结构化进度条与阶段展示 |

#### 3.1.2 选型对比

| 方案 | 优点 | 缺点 | 适配度 |
|---|---|---|---|
| **RQ**（Redis Queue） | 极简、Redis 单依赖、有 job 状态、取消方便、调试直观 | 不支持复杂编排（chain/group）、无原生定时 | ★★★★★ P0/P1 |
| **Celery** | 功能全（beat 定时、chain、路由、多队列） | 重、配置复杂、错误栈难读、单机场景过剩 | ★★★☆ 后期 |
| **Dramatiq** | 比 Celery 简洁，支持重试/优先级 | 中文资料少，与 Flask 集成需自写 | ★★★ |
| **自研线程池 + Redis** | 完全可控 | 要自己实现重试、心跳、崩溃恢复、并发控制 | ★★ 不推荐 |

**推荐：RQ + APScheduler，理由如下**

1. 单机 64G 场景，任务量级是"每天几十个报告 + 每 15 分钟一批预警扫描"，**用不到 Celery 的分布式能力**；
2. RQ 的 job 状态、失败重试、`cancel` 都是内置的，正好对应 `core.task` 的状态机；
3. 定时需求（预警扫描）用 APScheduler 单独跑，比引入 Celery Beat 更轻；
4. **迁移成本低**：`ReportEngine` 现在是 `threading.Thread(target=...)`（`flask_interface.py:671` 附近），换成 `queue.enqueue(func, ...)` 是同一形状的替换。

> ⚠️ 待验证：RQ 在 Windows 开发机上有 fork 限制（官方建议 Linux/WSL）。目标机是 Ubuntu，不受影响；但开发同学本地调试需要 WSL。

#### 3.1.3 任务状态机

```text
queued ──► running ──► succeeded
   │          │
   │          ├──► waiting_input（需要人工确认实体/补充材料）
   │          │         └──► running
   │          ├──► failed（可重试 → queued）
   │          └──► canceled
   └──► canceled
```

**心跳机制**：worker 每 15 秒更新 `heartbeat_at`；调度器每 60 秒扫描 `status='running' AND heartbeat_at < now() - 2min`，判定为僵死，置 `failed` 并允许重试。这是 RQ 不自带、必须自己补的部分。

#### 3.1.4 改造点清单

| 改造项 | 位置 | 工作量 | 说明 |
|---|---|---|---|
| 引入 Redis + RQ worker | 新增 `worker/` | 3 人日 | 独立进程，`rq worker dd pr` 双队列（背调慢、舆情快，避免互相阻塞） |
| `ReportEngine` 任务去单例 | `ReportEngine/flask_interface.py:31-32`、`:605-696` | 4 人日 | `current_task` → `task_store`（Redis Hash，key=task_id） |
| 引擎执行体抽离 Streamlit | `SingleEngineApp/*.py` 三份 | 6 人日 | 方案 A §7.1 的 `runner` 方案：`on_progress` 回调替代 `st.progress` |
| 进度结构化 | 新增 `core.task_step` 写入 | 2 人日 | 从 loguru 日志里抽阶段标记，或直接改 runner 埋点 |
| SSE 进度流 | 复用 `flask_interface.py:750` 的既有范式 | 2 人日 | 已有 SSE 实现，改成读 `task_step` 即可 |
| 取消与超时 | 新增 | 2 人日 | RQ `cancel` + 任务级 `timeout` |

**小计约 19 人日**（不含前端）

#### 3.2.3 授权判定策略

**双层：应用层过滤 + 数据库 RLS 兜底。**

- 应用层：每个查询自动注入 `project_id IN (我的项目)`，这是主路径，好调试
- 数据库层：对 `core.task` / `core.evidence` / `core.artifact` 开 `ROW LEVEL SECURITY`，用 `SET LOCAL app.user_id` 传身份

```sql
ALTER TABLE core.task ENABLE ROW LEVEL SECURITY;

CREATE POLICY task_project_isolation ON core.task
    USING (
        project_id IN (
            SELECT project_id FROM core.project_member
            WHERE user_id = current_setting('app.user_id', true)::BIGINT
        )
    );
```

> **为什么要双保险**：单靠应用层，任何一处忘记加过滤条件就是越权；RLS 让"忘记"变成"查不到"而不是"查多了"。代价是每条请求要多一次 `SET LOCAL`，可忽略。
>
> ⚠️ 待验证：RLS 对连接池（PgBouncer transaction 模式）不友好，需确认平台连接方式；若用连接池，改为应用层过滤 + 关键接口二次校验。

#### 3.3.2 埋点位置

| 层 | 方式 | 说明 |
|---|---|---|
| HTTP 入口 | Flask `before_request` / 统一装饰器 | 记录"谁调了哪个接口"，覆盖所有 API |
| 数据变更 | SQLAlchemy `after_update` 事件 | 记录字段级变更（只记字段名，不记正文） |

#### 3.3.3 三条原则

1. **不记正文**：只记 `evidence_id` / `artifact_id`，避免审计表变成第二份数据副本（体积与合规风险）
2. **不可修改**：审计表只 `INSERT`，应用账号无 `UPDATE/DELETE` 权限
3. **可检索**：按"人 / 时间 / 对象"三轴都能查，否则出事时等于没有

## 4. 前端方案

### 4.1 技术栈建议

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | **React 18 + TypeScript + Vite** | 生态最大，TipTap/G6/ECharts 都有成熟 React 封装；TS 对复杂数据模型（四类实体、任务状态机）是刚需 |
| UI 库 | **Ant Design 5** | 企业后台场景最成熟：表格/表单/日期范围/树形/抽屉齐全；`Table` 支持虚拟滚动，够用到十万行 |
| 路由 | React Router 6 | 标配 |
| 服务端状态 | **TanStack Query v5** | 任务列表、告警队列天然是"轮询 + 缓存 + 失效重取"，手写 `useEffect` 会失控 |
| 客户端状态 | Zustand | 轻，只存 UI 态（侧栏折叠、当前选中证据） |
| 编辑器 | **TipTap（ProseMirror）** | 唯一能干净支持"自定义行内节点（证据角标）"的成熟方案；Markdown 输出天然 |
| 图表 | ECharts 5 | 声量曲线、情感走势、时间轴 |
| 关系图 | AntV G6 | 股权穿透、传播路径；比 ECharts graph 更适合交互 |
| 请求 | axios + 拦截器 | 统一 401/403/错误码处理 |

**关于 Vue**：技术上 React 与 Vue 对本案**没有决定性差异**。决策依据应该是**团队既有栈**。如果团队是 Vue 系，等价替换为 `Vue 3 + Element Plus + Pinia + TanStack Query(Vue) `，TipTap/G6/ECharts 完全通用。**不要为了"新"而选不熟的栈**——这个项目的前端复杂度在后端，不在框架。

#### 4.2.2 迁移三阶段

```text
阶段 1（并行期）
  /           → 旧 index.html（保留）
  /app        → 新前端（背调工作台）
  Streamlit 三个端口：仍自动启动，供旧页面用

阶段 2（切换期）
  /           → 重定向到 /app
  /legacy     → 旧 index.html（只读，能看历史，不能再发起分析）
  Streamlit：改为手动启动，不再由 app.py 自动拉起

阶段 3（收尾）
  删除 /legacy 与三个 iframe 相关代码
  Streamlit：仅保留 `python -m streamlit run SingleEngineApp/xxx.py` 与 debug 开关
```

**Stage 2 的关键动作**：删掉 `app.py:277-348` 里"自动启动三个 Streamlit"的逻辑。这样做的直接收益：

- 主应用启动从"拉起 3 个 Streamlit + 等 30 秒就绪"变成秒级
- 内存从"主应用 + 3 个 Streamlit（112–456MB each）"降到只留主应用
- 不再需要 8501/8502/8503 三个端口暴露到公网

#### 4.2.3 Streamlit 的降级定位

**保留它，但彻底退出生产链路。** 定位改为：

- **调试工具**：开发同学本地验证某个引擎的 prompt 与工具调用
- **兜底入口**：主应用故障时，可手动起单个引擎做应急分析
- **不再承担**：用户入口、进度展示、报告交付

> 理由：三个 Streamlit 脚本里其实封装了完整的执行逻辑（方案 A §7.1），把它彻底删掉会把调试能力也删掉；降级为"手动启动的开发者工具"是投入产出最高的处置。

### 4.4 报告编辑与证据溯源交互

#### 4.4.1 三栏布局

已在 §4.3.1 页面 3 给出。核心是**证据抽屉不打断阅读**——用户点角标时视线不离开正文区域。

#### 4.4.2 编辑态的证据保护

这是最容易出问题的地方。四条规则：

1. **角标是原子节点**：TipTap 自定义 `citation` inline node，删除时整块删除，不会留下半个 `[E1`
2. **删角标 = 解除引用**，不删证据：`artifact_citation` 行变 `checked=false`，证据仍在证据库
3. **保存时校验**：
   - 每个 `block_type='paragraph'` 且含数字/金额/比例的段落，**至少 1 个 citation**，否则标黄提示"该段含事实性数据但无引用"
   - 所有 citation 的 `evidence_id` 必须存在且 `object_id` 与报告主体一致（防止串档）
4. **数字回查**（P1 加）：抽取正文中的数字，检查是否出现在对应 evidence 的 `quote` 里；不出现 → 标红"数字未在证据中找到"

#### 4.4.3 导出

| 格式 | 实现 | 注意 |
|---|---|---|
| HTML | 直接用 `artifact_block.content_html` 拼装 | 复用 `ReportEngine/renderers/html_renderer.py` 的样式 |
| PDF | WeasyPrint（方案 A 已确认可用） | 角标转上标数字，附录自动生成"证据索引" |
| Markdown | `content_md` 直接拼接 | 角标保留 `[E12]`，文末附 evidence 表 |
| Word/PPT | 待验证（方案 A §3 未覆盖） | P3 再做 |

**PDF 附录自动生成**：从 `artifact_citation` 反查 evidence，输出 `序号 | 事实 | 来源 | 发布时间 | URL`，**这是背调报告能被采信的关键一页**。

## 5. 业务功能设计

### 5.1 背调侧：三种模板

#### 5.1.1 模板对比

| 维度 | 投资尽调 | 人员背调 | 合作方准入 |
|---|---|---|---|
| 决策问题 | 能不能投 | 能不能用这个人 | 能不能合作 |
| 主体 | 公司 | 自然人（+ 其任职公司） | 公司 |
| 深度 | 最全（含财务、股权穿透） | 中（职务真实性、关联企业风险） | 中（合规、履约能力） |
| 时效 | 1–3 周 | 3–5 天 | 3–7 天 |
| 必查项 | 财务三表、股权结构、司法、行政处罚、知识产权 | 任职真实性、关联企业、涉诉、失信 | 存续状态、行政处罚、涉诉、招投标履约 |
| 输出 | 完整报告（12 章） | 简明报告（6 章） | 准入结论 + 风险清单 |

#### 5.1.2 评分卡维度

**投资尽调（100 分）**

| 维度 | 权重 | 关键指标 | 数据源 |
|---|---|---|---|
| 主体稳定性 | 10 | 存续年限、经营异常、法人变更频次 | 工商 |
| 股权结构 | 15 | 集中度、穿透层级、是否有代持迹象、实控人清晰度 | 工商 |
| 财务健康 | 25 | 营收增速、净利率、资产负债率、经营现金流、应收账款周转 | 巨潮/Tushare |
| 司法风险 | 20 | 被执行、失信、涉诉数量与金额、限高 | 裁判文书/执行公开 |
| 合规风险 | 15 | 行政处罚次数与金额、监管问询 | 信用中国/交易所 |
| 经营活跃度 | 10 | 招投标中标、对外投资、资质 | 招投标/工商 |
| 舆情风险 | 5 | 负面占比、重大负面事件 | bettafish 采集 |

**人员背调（100 分）**

| 维度 | 权重 | 关键指标 |
|---|---|---|
| 任职真实性 | 30 | 工商登记与公开披露是否一致 |
| 关联企业风险 | 25 | 其任职/持股的其他公司的风险传导 |
| 司法涉诉 | 20 | 个人被执行、限高、涉刑（仅公开） |
| 失信记录 | 15 | 失信被执行人、限制高消费 |
| 舆情 | 10 | 公开负面报道（需 ≥2 独立源） |

> **合规章节**：人员背调只查"与职业身份相关的公开信息"，不查个人生活。报告固定加一段"本报告仅基于公开工商与司法信息，不涉及个人隐私"。

**合作方准入（100 分）**

| 维度 | 权重 | 关键指标 |
|---|---|---|
| 主体资格 | 20 | 存续状态、经营范围匹配、资质 |
| 履约能力 | 25 | 招投标历史、中标率、合同纠纷 |
| 财务稳健 | 20 | 资产负债率、现金流 |
| 合规记录 | 20 | 行政处罚、失信、环保/安全处罚 |
| 关联风险 | 15 | 实控人风险、关联担保 |

#### 5.1.3 三态判定（关键设计）

每个维度**必须**输出三种状态之一，不能只有"得分"：

| 状态 | 含义 | 展示 | 计分 |
|---|---|---|---|
| 🟢 **无明显风险** | 有数据，且未触发风险规则 | 绿色 | 得满分 |
| 🔴 **确有风险** | 有数据，且触发风险规则 | 红色 + 具体事实 + 证据 | 按规则扣分 |
| ⚪ **数据缺失** | 无数据 / 数据过期 / 置信度 < 阈值 | 灰色 + "未获取到公开数据" | **不计分，且不按 0 分算** |

**计算逻辑**

```
有效维度 = 状态 ≠ 数据缺失 的维度
覆盖率 = Σ(有效维度权重)
得分   = Σ(有效维度得分 × 权重) / 覆盖率
```

**报告必须显著标注覆盖率**：
- 覆盖率 ≥ 80%：结论可用
- 60% ≤ 覆盖率 < 80%：结论仅供参考
- 覆盖率 < 60%：**强制拒绝出结论**，只输出"证据不足清单"

> **这是产品诚信的底线**：把"没查到"说成"没问题"，是背调类产品最常见的原罪。

**一票否决项**（不受权重影响，直接降级）：
- 失信被执行人 / 吊销 / 注销
- 实控人被采取强制措施（公开信息）
- 近 1 年重大安全生产事故或环保处罚

#### 5.1.4 合规表述规范

| 禁止 | 改用 |
|---|---|
| "该公司必然爆雷" | "公开信息显示其存在……迹象，建议关注" |
| "法定代表人张三有诈骗前科" | "公开裁判文书显示，张三曾涉及……案件（案号 XXX），判决结果为……" |
| "这是一家空壳公司" | "该公司社保缴纳人数为 0，且无公开经营场所信息" |
| "竞争对手在背后推动" | "传播呈现同步特征，是否人为组织需进一步核实" |

**报告内固定分隔**：
- 【事实陈述】—— 有 evidence 支撑，可直接引用
- 【分析意见】—— 基于事实的推断，标注"本报告分析意见，不构成事实认定"

### 5.2 舆情侧：事件发酵归因框架

#### 5.2.1 四层归因

**① 源头识别**

| 问题 | 判据 | 数据 |
|---|---|---|
| 谁最先发？ | 全量数据中 `published_at` 最小，且内容非转载 | 各平台首条记录 |
| 有没有原始素材？ | 是否含一手图片/视频/文件（而非截图转述） | 内容解析 |
| 是否回流？ | 首发在社交平台 → 后进入媒体，说明社交驱动；反过来是媒体驱动 | 时间序列 + 来源类型 |
| 是否旧闻翻炒？ | 内容哈希/语义与历史事件匹配 | evidence 库比对 |

**② 传播节点**

| 指标 | 说明 |
|---|---|
| 关键节点 | 单条转发/引用量 Top-5 的账号，及其类型（媒体/大V/机构/普通） |
| 平台跃迁路径 | 如 微博 → 抖音 → 门户 → 电视，每一跳的时间差 |
| 扩散速度 | 从首报到峰值的小时数 |
| 层级深度 | 原始 → 二次加工 → 三次评论 |

**③ 情绪转折点**

| 指标 | 算法 |
|---|---|
| 情感序列 | 按小时聚合情感均值（−1…+1） |
| 变点检测 | CUSUM 或 PELT（方案 A §8.2.3 已列） |
| 转折归因 | 转折时刻前后 ±2 小时的**新增高影响力内容**，人工确认触发源（官方回应？二次爆料？） |
| 主导情绪迁移 | 愤怒 → 嘲讽 → 同情 这类迁移比"均值"更有信息量 |

**④ 推手判断（合规红线）**

**只能描述可观测特征，不能定性"水军"。**

| 可观测特征 | 说明 | 表述方式 |
|---|---|---|
| 账号同步性 | 同一批账号在多个不相关事件中重复出现 | "存在账号重叠现象" |
| 注册时间集中 | 参与账号注册时间聚集在某短窗口 | "账号注册时间分布集中" |
| 内容同质 | 文本相似度 > 0.9 的比例异常高 | "内容高度同质" |
| 发布时间规律 | 发布间隔呈机械规律（如整分钟） | "发布节奏呈现规律性" |

**输出模板**：
> "本次传播呈现以下特征：A、B、C。**上述特征可用于辅助判断，但不足以认定存在有组织操纵**。如需进一步确认，建议结合平台侧数据。"

> 这条红线必须写进产品的 prompt 与人工审核清单。一旦报告写成"XX 公司雇佣水军"，法务风险远大于产品价值。

#### 5.2.2 预警分级与响应

| 级别 | 触发条件（示例） | 响应时限 | 值班动作 | 通知 |
|---|---|---|---|---|
| **P0** | 央媒/监管点名；产品安全事故；高管涉案；3σ 声量爆发 + 负面 > 50% | **30 分钟** | 立即上报 + 启动预案 | 电话 + 企微 + 短信 |
| **P1** | 单平台 3σ 爆发且负面 > 40%；行政处罚公示；权威媒体质疑 | **2 小时** | 值班员核实 + 拟定口径 | 企微 + 邮件 |
| **P2** | 负面占比抬升；单一媒体质疑；竞品对比提及 | **当日** | 记录 + 日报 | 日报汇总 |
| **P3** | 零星负面 | **本周** | 归档 | 周报 |

**分级必须可解释**：`alert_record.payload` 存触发时的指标快照，前端展示"为什么是 P0"。

> **v1.1 修订（决策③）**：预警后移至 P3，检测粒度定位 **2 小时级轮询**（APScheduler，非实时流式）。上表的"响应时限"只能从**系统发现时刻**起算——P0 的"30 分钟"在 2h 轮询下不可达成（发现时事件可能已发酵 2 小时），应修订为"P0 级事件发现后 2 小时内完成首响与上报"。若未来业务收紧到 30 分钟级，采集架构需重新评估（流式 vs 轮询），这是本设计唯一可能因时效要求返工的点。

### 5.3 应急预案结构

方案 A §8.4.1 已给出 `kb.playbook` / `kb.playbook_step` 的表结构。本节补**业务内容结构**（六段式）：

| 段 | 内容 | 示例 |
|---|---|---|
| **1. 触发条件** | 什么事件类型 + 什么级别 + 什么行业 | 产品安全事故 + P0 + 消费品行业 |
| **2. 响应动作** | 按时间窗分组的具体动作 | 0–2h：成立应急小组、封存证据、暂停相关宣传；2–24h：发布首份声明、开通客服专线；1–7d：整改方案、媒体沟通 |
| **3. 责任矩阵（RACI）** | 每个动作谁负责/谁审批/谁配合/谁知会 | 声明发布：公关部 R、法务 A、业务 C、CEO I |
| **4. 话术库** | 分场景的标准表述 | 对外声明模板 / 客服话术 / 内部通报 / 媒体应答 Q&A |
| **5. 时间轴** | 关键节点与法定时限 | 如"重大事故 1 小时内上报监管部门" |
| **6. 复盘模板** | 事件结束后必填 | 起因 / 处置得失 / 改进项 / 责任人 |

**话术库是预案的核心价值**——真出事时没人有心情写文案，能直接取用才叫预案。

### 6.1 P0：最小可交付（先证明链路通）

## 7. 风险与开放问题

### 7.1 五个最可能导致返工的风险

| # | 风险 | 为什么会返工 | 缓解 |
|---|---|---|---|
| 1 | **进度结构化被低估** | 现在进度是 Streamlit 自己画的 + loguru 打的文本日志，抽成 `task_step` 需要改三个引擎的执行体。如果先做前端、后补后端，前端要重做两遍 | **P0 先做后端骨架，前端接 SSE；不允许"先用假数据做前端"** |
| 2 | **实体对齐错误导致整卷作废** | 背调报告的所有结论都挂在 `object_id` 上，一旦对象选错，整份报告要重出 | 新建案卷时强制人工确认对象（§4.3.1 页面 2）；`confidence < 92` 必须人工选 |
| 3 | **双轨期维护成本** | 旧 index.html + 新前端并行，两个入口两套 bug | 并行期严格限定 1 个迭代（≤3 周），到期强制切 `/app` |
| 4 | **报告格式漂移** | LLM 输出结构不稳定，编辑器/校验需要容错；若要求"结构化 JSON 严格匹配模板"，失败率高 | 采用「模板骨架 + LLM 填段」而非「LLM 出整篇」；每章独立生成独立校验 |
| 5 | **合规表述失控** | 推手判断、风险定性一旦越界，是法务风险不是技术风险 | 禁用词表 + 报告固定分隔【事实】/【意见】+ 定稿前人工过审 |

### 7.2 已决策项与剩余开放问题（v1.1 更新）

**已决策（2026-11-08，详见 §0.1）**：

| 原开放问题 | 决策 | 落点 |
|---|---|---|
| Q1 用户规模 / Q4 企微内打开 | 仅内部使用，不对客户部署，只对客户出报告 | RBAC 简化为两层（P1，8→5 人日）；砍移动端/SSO/多租户/对外 API（−19 人日）；报告 PDF 与合规表述升级为对客户门面 |
| （新增）数据采购预算 | 未定，先免费额度做 demo，后续申请 | P0/P1 限定免费源（§6.1）；评分卡三态为必需品；付费源留接口热插 |
| Q3 预警对象与时机（部分） | 预警暂不做，后续 2 小时级别 | 预警后移 P3；2h 轮询 = APScheduler，不引入流式架构；「固定名单 vs 全行业扫描」到 P3 启动前再定即可 |

**剩余开放问题（2 条）**：

1. **报告是否需要人工编辑后发布**？
   → 决定 TipTap 编辑器（10 人日）的优先级。若"LLM 出稿直接导出"，可以砍掉，P2 省 10 天。考虑到报告是对客户唯一交付物（决策①），**倾向保留人工编辑**，但可先导出后编辑（P2 顺序可调）。

2. **是否有存量报告需要迁移**？
   → 现有 `final_reports/` 下的历史 HTML 若要进新系统，需要反向抽 `artifact_block` 与 `evidence`，是独立工作量（约 5 人日），且抽出来的证据链不完整（当时没存）。
